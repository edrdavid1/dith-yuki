# Задача: фикс шва DitherV2 Floyd-Steinberg/Atkinson (видно на всех zoom, включая 1:1)

## Контекст

Диагностика подтвердила: `requires_full_row` для DitherV2 выставляется корректно,
race condition не портит результат (детерминированность), `clear()` всегда парен
с dirty-меткой. То есть при уже прогруженных raw-тайлах на 1:1 фильтр должен быть
почти бесшовным — но пользователь видит шов **на всех zoom, включая 1:1**.

Это исключает пункт A из прошлой диагностики (`level == 0` enforcement — объясняет
швы только на отдалении, не на 1:1). Главный подозреваемый — **пункт B**:

`tile_pipeline.rs:120` и `:146` — рекурсия для получения residual соседа выполняется
только `if state.tile_cache.get_entry(*_raw_key).is_some()`. Если raw-тайл соседа ещё
не в кэше в момент обработки текущего тайла, зависимость **молча пропускается**:
`get_left`/`get_top` возвращают `None`, используется нулевой seed вместо реального
residual — и это шов. Критично: **ничего не помечает текущий тайл dirty**, когда
raw соседа позже становится доступен. Шов остаётся до следующей ручной инвалидации
(смена параметра фильтра, zoom и обратно и т.п.) — то есть залипает, что объясняет,
почему он виден стабильно, а не только при первой загрузке.

## Шаг 1. Подтвердить гипотезу B репродукцией

Нужно различить два сценария:

1. **Шов появляется даже после полной прогрузки** (открыть документ, подождать
   пока всё догрузится на 1:1, зум туда-обратно чтобы гарантированно всё в кэше,
   ТОЛЬКО ПОТОМ включить/посмотреть DitherV2) — если шов всё ещё есть, дело не
   только в B, надо смотреть глубже (возможно другой баг в самой передаче residual,
   а не в его отсутствии).
2. **Шов появляется при быстрой навигации/панорамировании**, когда тайлы догружаются
   не мгновенно, и остаётся зависшим даже после полной догрузки области — это прямое
   подтверждение B: тайл посчитался раньше соседа, licenseа на пересчёт не было.

Добавить лог/счётчик: сколько раз за сессию сработала ветка "raw соседа нет в кэше,
residual = 0" (в `tile_pipeline.rs` рядом с `.is_some()` проверкой). Открыть документ,
попанорамировать активно, посмотреть счётчик — если > 0, это происходит регулярно
в реальном использовании, не только в теории.

Записать результат обоих тестов в комментарий к PR перед тем как переходить к фиксу.

## Шаг 2. Фикс B — переинвалидация зависимого тайла, когда сосед догружается

Идея: вместо того чтобы молча пропускать зависимость, нужно **зарегистрировать
ожидание** и переинвалидировать тайл, когда недостающий raw-сосед появится в кэше.

1. Найти в `tile_pipeline.rs` место, где обрабатывается загрузка/появление нового
   raw-тайла в `tile_cache` (событие "raw tile loaded" / `insert` в кэш для raw-слоя).
2. Завести структуру ожидания, например:

```rust
// В состоянии пайплайна (там же где ErrorResidualsStore/tile_cache)
// key: raw_key соседа, которого ждут; value: список ключей тайлов,
// чья error-diffusion обработка от него зависела и была вычислена с нулевым seed
pending_diffusion_waiters: DashMap<TileKey, Vec<TileKey>>,
```

3. В месте, где сейчас `if state.tile_cache.get_entry(*_raw_key).is_some() { ... }
   else { /* молча пропускаем */ }` — в ветке `else` дополнительно
   зарегистрировать текущий тайл как ожидающего в `pending_diffusion_waiters`
   под ключом `*_raw_key`.
4. В обработчике "raw tile loaded в кэш" — после вставки проверить
   `pending_diffusion_waiters.remove(&loaded_raw_key)`, и если есть ожидающие —
   пометить их dirty / поставить на пересчёт через тот же механизм, которым обычно
   инвалидируются тайлы при смене параметров (найти существующий `mark_dirty`/
   `invalidate` вызов и переиспользовать его, не изобретать новый путь).
5. Граничный случай: тайл может успеть попасть в ожидание сразу нескольких соседей
   (и left, и top raw не готовы) — регистрировать во всех соответствующих списках,
   снимать зависимость по мере готовности каждого, пересчитывать когда снята
   последняя (или просто пересчитывать при первом же уведомлении и полагаться на
   то, что повторный пересчёт всё равно корректен, если это дешевле по объёму
   изменений — уточнить у существующей архитектуры invalidation, не дублировать
   логику).

## Шаг 3. Заодно фикс A — enforcement на всех pyramid levels

Раз работаем в этом файле — закрыть и второй подтверждённый баг, чтобы не возвращаться:

`tile_pipeline.rs:97`: `if has_error_diffusion && key.coord.level == 0` — убрать
ограничение `level == 0`, enforcement соседей должен работать на любом pyramid level.
Проверить, не завязана ли остальная логика (`ErrorResidualsStore` ключи, `get_left`/
`get_top`) на предположение "level всегда 0" — если завязана, ключи должны включать
`level` в идентификацию тайла (похоже, `TileCoord` уже содержит `level`, судя по
предыдущей задаче — значит просто убрать проверку должно быть достаточно, но
перепроверить).

## Шаг 4. Тесты

1. Юнит-тест на pending_diffusion_waiters: тайл A запрашивает residual соседа B,
   B ещё не в кэше → residual = 0, A зарегистрирован как waiter. Затем B появляется
   в кэше → A должен быть помечен dirty. Проверить через мок/тестовый tile_cache.
2. Интеграционный/визуальный тест: тот же сценарий 2×2 тайла что и в прошлой задаче,
   но с искусственной задержкой загрузки raw-тайла (X+1, Y) относительно (X, Y) —
   после того как оба догрузятся и пересчитаются, результат должен побитово совпадать
   с рендером, где оба raw-тайла были в кэше с самого начала.
3. Regression: убедиться что счётчик из Шага 1 либо равен нулю после фикса (зависимость
   правильно ожидается и пересчитывается), либо больше не оставляет видимых швов.

## Критерии приёмки

1. Шаг 1 выполнен, результат репродукции задокументирован (какой из двух сценариев
   подтвердился).
2. Шов на 1:1 после полной догрузки области — отсутствует (визуально и по тесту Шага 4.2).
3. Enforcement работает на всех pyramid levels (Шаг 3), шов при отдалении тоже исчезает.
4. Новые юнит- и интеграционные тесты зелёные, старые 57+14 тестов dither/coords не сломаны.
