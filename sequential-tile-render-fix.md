# Тайлы рендерятся последовательно (растровый порядок), а не параллельно center-out

## 1. Диагноз: где искать причину

Симптом «заполняется от левого столбца вниз, не одновременно» почти наверняка **не про backend-параллелизм** (N worker-потоков там реально есть и реально считают тайлы одновременно), а про то, что **запросы на фронте отправляются не одновременно**. Это разные вещи: можно иметь идеально параллельный `rayon`-пул на бэке и всё равно увидеть строго последовательное появление тайлов, если фронт спрашивает их по одному.

Два независимых места, где может быть последовательность вместо параллельности — проверить оба:

### 1.1 Самая вероятная причина: `tileWorker.ts` запрашивает тайлы в цикле с `await`

Если реализация выглядит так (стандартная ошибка, которая выглядит рабочей на глаз, но убивает параллелизм):

```typescript
// ПЛОХО — каждый следующий fetch стартует только после завершения предыдущего
for (const tile of tiles) {
  const bitmap = await fetchAndDecodeTile(tile); // <-- сериализация здесь
  postMessage({ type: 'tile-decoded', key: tile.key, bitmap }, [bitmap]);
}
```

— то результат будет ровно тем, что вы наблюдаете: тайлы «капают» по одному в порядке, в котором их перечислил `computeVisibleTiles` (а это обычно nested-loop `for x { for y { ... } }`, то есть буквально «столбец за столбцом сверху вниз» — это и есть «растровый порядок» из симптома). При этом backend может параллельно посчитать хоть все тайлы разом — не имеет значения, если фронт не шлёт следующий HTTP-запрос, пока не получит ответ на текущий.

**Фикс** — firing all requests concurrently, без await между ними:

```typescript
// ХОРОШО — все запросы улетают сразу, ответы приходят по готовности, в любом порядке
await Promise.all(
  tiles.map(async (tile) => {
    const bitmap = await fetchAndDecodeTile(tile);
    postMessage({ type: 'tile-decoded', key: tile.key, bitmap }, [bitmap]);
  })
);
```

Здесь важно: `postMessage` вызывается **из каждой параллельной ветки сразу по готовности**, а не после того, как все они завершатся (то есть не `Promise.all(...).then(postAll)`), иначе вы уберёте последовательность запросов, но добавите ожидание самого медленного тайла перед показом всех остальных — это другая, тоже плохая форма «неодновременности».

### 1.2 Вторая возможная причина: приоритет внутри одного «bucket» — это по сути FIFO в порядке enqueue

Даже если фронт шлёт все запросы параллельно, порядок, в котором worker-пул их **обработает**, зависит от `Scheduler` (§4.1.5 архитектурного документа). Там 4 приоритета — `Immediate / ViewportCenter / ViewportEdge / Prefetch` — но **внутри** одного приоритета это `SegQueue`, то есть строгий FIFO. Если весь видимый viewport при классификации попадает в один и тот же bucket `ViewportCenter` целиком (то есть `classify_priority` не различает «в центре» и «на краю» тайлы видимой области, а просто маркирует «все видимые = Center, кольцо вокруг = Prefetch»), то порядок обработки внутри bucket'а — это порядок `enqueue`, то есть снова порядок, в котором `compute_visible_tiles` их перечислил (тот же nested loop). Даже при полностью параллельных запросах с фронта это создаёт **иллюзию** последовательности, потому что первый worker, освободившийся раньше других, будет выхватывать из FIFO именно в этом порядке, и на медленных участках (глубокий стек фильтров) видимый эффект — «сначала левый столбец, потом следующий» и так далее, просто потому что все N воркеров одновременно грызут одну и ту же голову очереди в её естественном порядке.

**Фикс** — сортировать enqueue-порядок внутри viewport по расстоянию от центра **до** постановки в очередь, а не полагаться на estественный порядок enumeration:

```rust
// в set_viewport, перед enqueue:
let center = (viewport.center_tile_x(), viewport.center_tile_y());
let mut visible = compute_visible_tiles(&viewport);
visible.sort_by_key(|coord| manhattan_distance(coord, center)); // от центра наружу
for coord in visible {
    scheduler.enqueue(RecomputeTask { key: TileKey { .. coord }, priority: Priority::ViewportCenter, .. });
}
```

Это ровно то поведение, которое было изначально описано в самом первом архитектурном документе («приоритет от центра к краям» через generation-очередь), но в текущей реализации, судя по описанию `classify_priority`, различие идёт только на уровне 4 грубых bucket'ов, а не непрерывного ранжирования внутри viewport — отсюда и «неодновременность» даже при наличии приоритетов как класса.

Если хочется честного «расползания из центра», а не просто «более правильного FIFO порядка», можно заменить `SegQueue` на бинарную кучу с ключом = дистанция от центра (не 4 дискретных уровня, а непрерывный score) — но это уже апгрейд, а не баг-фикс; §1.1+сортировка из §1.2 сами по себе уже решают наблюдаемый симптом.

## 2. Как проверить, какая из двух причин реальна

Не гадать, а быстро отличить:
- Если в `tileWorker.ts` есть `for`/`for...of` с `await fetch` внутри без `Promise.all` — это причина §1.1, и именно она даёт эффект «видно, что раньше отрисовывается тайл N, чем отправлен запрос на тайл N+1» (можно проверить через Network-таймлайн в devtools: запросы идут друг за другом, а не пачкой).
- Если в Network-таймлайне все `tile://` запросы стартуют одновременно (пачкой), но тайлы всё равно **применяются на канвасе** в строгом порядке — тогда это §1.2 (порядок обработки на бэке), и тут смотреть на `classify_priority`/`Scheduler::enqueue`, а не на фронтенд-код.

Практически весьма вероятно, что проблема — именно §1.1 (это самая частая причина именно такого симптома в tile-viewer коде), но §1.2 стоит исправить в любом случае — это то же самое отклонение от изначально согласованного «приоритет от центра, а не от порядка enumeration», которое всплывало и в предыдущем баг-репорте.

---

## 3. Итог

Обе причины лечатся без архитектурной перестройки:
1. `Promise.all` вместо последовательного `await`-цикла в `tileWorker.ts` — с `postMessage` из каждой ветки индивидуально, не пачкой в конце.
2. Сортировка видимых тайлов по расстоянию от центра **перед** enqueue в `set_viewport` — чтобы даже FIFO внутри одного priority-bucket давал center-out порядок, а не порядок построчного перечисления сетки.

Это ортогонально трём багам из предыдущего документа (dirty→202, дублирование visible-tiles, `clear_all()`) — можно чинить параллельно, конфликтов между фиксами нет.
