# Бриф для агента: старт разработки

Этот документ — вход для агента (Claude Code или аналог), который будет писать код. Он не дублирует архитектуру, а объясняет **что делать и в каком порядке**, ссылаясь на уже готовые документы:

- `tile-engine-architecture.md` — тайловый движок, пирамида, кеш, инвалидация, планировщик.
- `tauri-api-document-model.md` — модель `Document`, команды `invoke`, протокол `tile://`, события.

Оба файла — источник истины по архитектуре. Если во время реализации что-то в них противоречит здоровому смыслу или Rust-экосистеме — агент останавливается и уточняет, а не тихо переделывает архитектуру по-своему.

---

## 1. Что мы строим (коротко, для контекста агента)

Кроссплатформенное десктоп-приложение (Windows/macOS/Linux) для художественной обработки фото и видео: дизеринг, глитчинг, точный цвет, слои, палитры. Ключевое требование — не «ещё один фоторедактор», а **pixel-perfect и мгновенная реакция UI** даже на файлах 5000×5000+ с 10+ слоями. Это определяет архитектуру (тайлы + пирамида + кеш с поколениями), а не наоборот — поэтому движок пишется раньше UI, и вообще большая часть сложности — в Rust-бекенде, фронтенд сравнительно тонкий.

## 2. Технологический стек

| Слой | Технология | Зачем именно это |
|---|---|---|
| Оболочка приложения | **Tauri 2** | Нативный WebView вместо Electron — меньше памяти, доступ к кастомным URI-протоколам (нужно для `tile://`) |
| UI | **React + TypeScript** | Панели слоёв, слайдеры; сам холст — не React-компонент с состоянием на пиксель, а `<canvas>`/`ImageBitmap` в Web Worker |
| Бекенд-движок | **Rust** | Производительность (5 мс/тайл — не обсуждается на других языках), `unsafe`-контроль над памятью для больших буферов |
| Параллелизм | `rayon` | Пул воркеров для тайлов, work-stealing из коробки |
| Конкурентные структуры | `dashmap`, `arc-swap`, `crossbeam-channel` | Кеш тайлов и `Document`, как описано в обоих документах |
| Цвет | `lcms2` | ICC-профили; `f32`/`half` (f16) для внутреннего представления |
| Изображения (кодеки) | `image`, `webp` (или `libwebp-sys`), `png` | Загрузка входных форматов, сжатие тайлов под `tile://` |
| Видео | `ffmpeg-next` (биндинги к системному/статическому ffmpeg) | Декод кадров |
| Сериализация | `serde` + `serde_json` (DTO на фронт), `bincode`/кастомный бинарный формат (тайлы в файле проекта) | JSON — только для метаданных, не для пикселей |
| Формат проекта | **SQLite** через `rusqlite` | Причина выбора именно SQLite vs ZIP — решается в следующем архитектурном документе; агент не начинает эту часть раньше времени |
| Тесты | `cargo test` + criterion для перф-тестов тайлового движка | Раздел 8 ниже |

Версии пакетов агент фиксирует сам на момент старта (`cargo add` без явного номера, затем зафиксировать в `Cargo.lock`) — в этом документе версии специально не прибиты, чтобы не устареть раньше кода.

## 3. Структура репозитория

```
/app                      # Tauri-обёртка: main.rs, tauri.conf.json, регистрация protocol handler
/crates
  /engine-core            # Document, Layer, LayerGroup, Filter*, BlendMode — из tauri-api-document-model.md §2
  /engine-tiles            # TileCache, TileKey, GenerationTracker, планировщик — из tile-engine-architecture.md
  /engine-color            # ICC, LUT, линейное пространство — БУДУЩИЙ блок, пока пустой крейт с TODO
  /engine-io               # кодеки изображений, ffmpeg — БУДУЩИЙ блок
  /engine-project          # формат проекта/SQLite — БУДУЩИЙ блок
/frontend                 # React + TS
  /src/canvas              # рендер тайлов, Web Worker, tile:// fetch-клиент
  /src/panels              # слои, фильтры, палитры
  /src/state               # тонкий стейт (снапшот документа с бека), НЕ источник истины по пикселям
/docs
  tile-engine-architecture.md
  tauri-api-document-model.md
  (этот файл)
```

Разбивка на отдельные `crates` внутри Rust-воркспейса — не бюрократия, а способ гарантировать инвариант «фронтенд не видит сырые пиксели» и «движок цвета не знает про Tauri» на уровне компилятора, а не code review: `engine-tiles` не должен зависеть от `tauri`, `app` — единственный крейт, который знает про IPC.

## 4. Порядок реализации (фазы)

Каждая фаза — это то, что агент делает **до** следующего чекпоинта с человеком. Внутри фазы агент работает самостоятельно; между фазами — ревью.

### Фаза 0 — Скелет
- `cargo new` воркспейс с крейтами из §3 (пустые, только `Cargo.toml` и заглушки).
- Голый Tauri-проект, открывающий окно. Без UI-логики.
- Definition of done: `cargo build` и `npm run tauri dev` поднимают пустое окно.

### Фаза 1 — Тайловый движок без UI (по `tile-engine-architecture.md`)
- `TileKey`, `TileCoord`, `PixelTile`, `TileCache` с `dirty`/`generation` — §1–3 документа.
- Пирамида: downsample уровня N из уровня N-1 (без слоёв пока — просто на одном растровом буфере).
- Приоритетная очередь и `rayon`-пул воркеров — §5.
- **Тестируется юнит-тестами и criterion-бенчами БЕЗ Tauri и без UI** — это чистая Rust-библиотека, гоняется из `cargo test`/`cargo bench` напрямую. Это специально вынесено раньше UI: если тут производительность не сойдётся с NFR (5 мс/тайл), дешевле узнать это сейчас, чем после того, как вокруг обрастёт UI-код.
- Definition of done: бенч показывает время пересчёта тайла 256×256 без фильтров и с синтетическим "тяжёлым" фильтром-заглушкой; инвалидация одного слоя не трогает несвязанные generation (тест на это явно, см. §5.1 документа).

### Фаза 2 — Модель документа и слои (по `tauri-api-document-model.md` §2)
- `Document`, `LayerNode`/`Group`, `Layer`, `FilterInstance` — структуры, без сериализации в Tauri ещё.
- `composite_tile` с реальным проходом по слоям снизу вверх, blend-моды (минимум Normal/Multiply/Screen для старта, остальные — по мере добавления, они однотипны).
- `arc-swap`-обёртка `DocumentHandle` — §5 документа.
- Definition of done: интеграционный тест — документ с 3 слоями и разными blend-модами даёт ожидаемый композит на известном тестовом изображении (golden image test — сохранить эталонный PNG и сравнивать побайтово/с допуском).

### Фаза 3 — Tauri-обвязка (по `tauri-api-document-model.md` §1, §4)
- Регистрация `tile://` протокола, привязка к `TileCache` из Фазы 1.
- Первые 3–4 команды `invoke`: `open_document` (с заглушкой загрузки — просто один растровый слой из файла), `set_viewport`, `update_filter_params`, `set_layer_props`.
- Событие `tile-ready`.
- Definition of done: можно из React дернуть `open_document`, увидеть в консоли снапшот, руками через `fetch('tile://...')` получить байты картинки.

### Фаза 4 — Минимальный фронтенд-холст
- Web Worker, который дёргает `tile://` для видимых координат и рисует через `ImageBitmap` на `<canvas>`.
- Один слайдер (например, яркость) как первый реальный `FilterInstance`, чтобы проверить полный цикл: слайдер → `update_filter_params` → инвалидация → `tile-ready` → перезапрос `tile://` → обновление канваса.
- Definition of done: **вертикальный срез работает целиком** на одном тестовом изображении — это первая точка, где стоит показать результат человеку, а не архитектурный документ.

### Фазы 5+ (не детализируем сейчас, порядок ориентировочный)
- Панель слоёв (add/remove/reorder/group) поверх уже готовых команд.
- Маски.
- Цветовой пайплайн (ICC/LUT) — отдельный архитектурный документ понадобится раньше кода.
- Формат проекта (SQLite) — тоже отдельный документ раньше кода.
- Палитры, пресеты.
- Видео — в последнюю очередь, т.к. в ТЗ помечено как «базовая поддержка» и меньше всего связано с остальным движком.

## 5. Что агент НЕ придумывает сам

- Схему БД проекта, формат ICC/LUT пайплайна, парсеры палитр (.ase/.aco/...) — эти блоки описаны в ТЗ как требующие детальной проработки, и у нас с архитектором есть план проработать их отдельными документами до того, как их кодировать. Если агент дойдёт до этой границы раньше, чем документ готов — сигнал остановиться, а не додумывать формат на ходу.
- Список конкретных 10+ blend-модов сверх Normal/Multiply/Screen/Overlay — согласовать по референсу (Photoshop/Krita), не изобретать формулы самостоятельно, т.к. пользователи будут ожидать привычное поведение.
- Точный порог `budget_bytes` для кеша и scratch-диска — зависит от целевого железа, не хардкодить произвольное число без пометки TODO/конфига.

## 6. Как агенту работать с двумя готовыми документами

- `tile-engine-architecture.md` — при написании кода Фазы 1, разделы читать в порядке §2→§3→§4→§5→§6 (структуры → кеш → halo → планировщик → композитинг).
- `tauri-api-document-model.md` — для Фаз 2–3, порядок §2→§5→§1→§4→§3 (сначала модель данных и конкурентность, затем транспорт и команды, DTO — в последнюю очередь, это производное от модели).
- Rust-код в документах — это **иллюстрация решения**, не финальный API один в один: сигнатуры можно уточнять (добавить `Result`, `Arc`, лишний параметр контекста), но описанное поведение (например: `update_filter_params` не блокируется на пересчёте, `dirty`-флаг вместо удаления) — это архитектурное решение, а не деталь реализации, и его менять нельзя без обсуждения.

## 7. Формат чекпоинтов с человеком

После каждой фазы агент присылает:
1. Что реализовано (кратко, по definition of done фазы).
2. Что пришлось уточнить/отклониться от документов и почему.
3. Что не сделано и почему (блокер, вне скоупа фазы, и т.п.).
4. Открытые вопросы к следующей фазе, если есть.

Без ожидания, что человек будет построчно ревьюить весь diff — акцент на архитектурные отклонения и открытые вопросы, а не на code review каждой строчки.

## 8. Тестовая стратегия (кратко, детализируется по ходу)

- `engine-tiles`, `engine-core`: юнит + criterion-бенчи, без UI, гоняются в CI на каждый PR.
- Golden-image тесты для композитинга и фильтров (сравнение с эталонным PNG, допуск на f32-погрешность).
- Перф-тест из НФР ТЗ (5000×5000, 10 слоёв, дизеринг+LUT) — не раньше, чем Фаза 2 будет пройдена целиком; ставится как отдельный milestone, не размазывается по фазам.
- E2E/UI-тесты — после того, как появится больше одного реального пользовательского сценария (не в первых 4 фазах).
