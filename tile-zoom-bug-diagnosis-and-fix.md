# Баг с тайлами при зуме: диагностика и план до уровня Photoshop

Хорошая новость: все три симптома из баг-репорта объясняются конкретными местами в уже описанной архитектуре (документ Dither Yuki 2, ревизия с `tile_protocol.rs`/`viewport.rs`/`worker.rs`), а не «общей природой тайлового рендеринга». Разберу каждый симптом → конкретную причину в коде → фикс, а в конце — что именно нужно, чтобы превью ощущалось как Photoshop (никогда не показывает пустоту, только всё более точную картинку).

---

## 1. Симптом «чёрные прямоугольники» (00:03, 00:05) — это регрессия относительно исходного архитектурного решения

### 1.1 Что происходит

В `tile_protocol.rs` (§3.3) логика такая:

> Проверка кэша: если entry существует и `!dirty` → 200 + RGBA8 bytes. Cache miss / dirty → enqueue Immediate task → 202 (empty body).

Это **прямое расхождение** с изначально согласованным решением из более раннего архитектурного документа (`tile-engine-architecture.md` §3.2):

> Тайл остаётся в кеше и продолжает рендериться (даже устаревший — лучше показать чуть старую картинку, чем пустоту)... Инвалидация — это не удаление, а пометка dirty.

То есть идея была: `dirty=true` не означает «нечего показать», это значит «есть немного устаревшие данные, покажи их, пока считается новое». В реализации же `dirty` тайл трактуется наравне с полным cache miss — оба отдают 202 с пустым телом. Отсюда:

- **Любая** инвалидация (смена zoom → новый уровень пирамиды → новый `TileCoord` → новый ключ кеша, значит формально это miss, не dirty, но эффект тот же) даёт пустой ответ на тайл, который *физически* мог бы быть посчитан из уже закешированных данных соседнего уровня, но протокол этого не делает.
- Пока `Immediate`-задача не выполнится (а очередь может быть занята другими задачами), фронт рисует ничего → чёрный прямоугольник.

### 1.2 Фикс

Разделить **три**, а не два случая в обработчике `tile://` (сейчас их два):

```rust
match cache.get(key) {
    Some(entry) if !entry.dirty.load(Ordering::Acquire) => {
        // Полностью актуально
        respond_200(entry.rgba8_bytes())
    }
    Some(entry) => {
        // dirty, но данные ЕСТЬ — отдаём их же, плюс планируем пересчёт
        cache.schedule(key, Priority::Immediate);
        respond_200(entry.rgba8_bytes()) // <-- ключевое отличие от текущей реализации
    }
    None => {
        // Реальный cache miss — вот тут действительно нечего отдать
        cache.schedule(key, Priority::Immediate);
        respond_202()
    }
}
```

После этого фикса 202 (и, соответственно, потенциальный чёрный кадр) остаётся только для **первого запроса тайла, которого вообще никогда не существовало** — что при нормальной работе prefetch/scheduler должно быть редким событием, а не происходить на каждое изменение zoom/фильтра.

## 2. Симптом «рассинхрон координат при зуме» (00:06) — дублирование логики visible-tiles на фронте и бэке

### 2.1 Что происходит

`compute_visible_tiles` реализован **дважды**, независимо:
- В Rust (`viewport.rs::set_viewport`, §3.4.4) — используется бэкендом для того, какие задачи ставить в scheduler.
- В TypeScript (`computeVisibleTiles`, §7.3) — используется фронтом для того, какие тайлы **запрашивать** через `tile://`.

Это две отдельные реализации одной и той же математики (floor/ceil, границы сетки, `tile_size_at_level`). Расхождение неизбежно на граничных случаях — собственно, баг-репорт прямо называет это третьей гипотезой («ошибка расчёта Bounding Box... особенно для крайних и нижних тайлов сетки»), и в вашем случае это не гипотеза, а структурная причина: даже если сегодня обе реализации совпадают, они обязаны совпадать *побитово* на всех округлениях, а любое будущее изменение одной без другой снова это сломает.

Отдельно: `set_viewport` вызывается с **debounce** на фронте (§7.8: `set_viewport IPC → debounced`), а обновление CSS-трансформации канваса — **немедленно** (§7.5 таблица: `immediate + set_viewport`). Значит в промежутке между «canvas уже показывает новый transform» и «backend посчитал новый visible-tiles список» фронт **уже** пытается запросить тайлы по *своей* немедленно пересчитанной сетке (через тот же `computeVisibleTiles`, независимо от debounce на IPC) — а backend ещё не в курсе нового viewport и планирует по старому. Верхний ряд «отрендерился с неправильным масштабом» (00:06) — это, скорее всего, именно кадр из этого переходного окна: часть тайлов отрисована по новой геометрии канваса, но данные под них ещё соответствуют старому viewport/уровню.

### 2.2 Фикс

**Убрать дублирование:** единственный источник истины по видимым тайлам — backend. `SetViewportResponse` должен возвращать не просто `{ level, tile_count }`, а явный список координат:

```rust
pub struct SetViewportResponse {
    pub level: u8,
    pub visible_tiles: Vec<TileCoordDto>,
    pub generation: u64, // снапшот viewport-generation на момент ответа
}
```

Фронт запрашивает через `tile://` **ровно** этот список, а не то, что сам пересчитал через параллельную TS-реализацию `computeVisibleTiles`. TS-функция остаётся только для *визуального* немедленного отклика канваса (transform/scale отрисовки уже загруженных бит-мапов), но не для того, какие координаты дёргать по сети.

**Синхронизировать debounce:** transform канваса можно обновлять немедленно (это чисто визуальный CSS/canvas transform поверх уже имеющихся битмапов — Photoshop так и делает при интерактивном зуме, показывая текущую картинку растянутой, пока не подъедут точные тайлы), но именно поэтому важно **не путать** «немедленно растянуть то, что уже есть» с «немедленно считать, какие новые тайлы запрашивать» — второе обязано ждать ответа `set_viewport` с окончательным списком координат, иначе получается ровно описанный рассинхрон.

## 3. Симптом «мерцание при инвалидации» (00:07) — `scheduler.clear_all()` на каждый viewport change

### 3.1 Что происходит

`viewport.rs`, шаг 5 (`8.3` sequence diagram): при каждом изменении viewport вызывается `scheduler.clear_all() + re-enqueue dirty`. `clear_all()` **дренирует все 4 очереди целиком** (§4.1.5: «drains all queues (used on viewport change to cancel stale tasks)»).

Проблема: это не выборочная отмена *устаревших* задач (для этого уже есть механизм — generation/staleness check при dequeue, который и так должен отбрасывать неактуальные задачи дёшево), а **полное уничтожение любой работы**, включая задачи, которые уже были в процессе и вот-вот произвели бы актуальный тайл для *нового* viewport (например, если новый viewport частично пересекается со старым — типичный случай при плавном зуме/пане). Тайлы, которые пересчитывались бы и без этого сброса, теперь надо планировать заново с нуля — отсюда лишняя задержка и, в сочетании с багом №1 (dirty → 202 пустой), видимое мерцание: старый тайл уже не отдаётся (не dirty, а вообще drained из очереди пересчёта), новый ещё не готов.

### 3.2 Фикс

Убрать `clear_all()` из `set_viewport` вовсе. Staleness-проверка на дequeue (`task.generation < current_gen`) — уже существующий и корректный механизм отмены; полная очистка очередей ему не нужна и вредна. Если беспокоит неограниченный рост очередей при частом дёрганье viewport — ограничивать это дедупликацией на **enqueue** (не добавлять задачу, если для этого же `TileKey` уже есть задача с priority ≥ новой), а не расстрелом всей очереди.

Если `clear_all()` был добавлен специально ради того, чтобы «выкинуть Prefetch/Edge задачи от старого viewport, которые больше не нужны» — это законная цель, но тогда чистить нужно избирательно: `clear_priority(Priority::Prefetch)` и `clear_priority(Priority::ViewportEdge)`, **никогда** не трогая `Immediate`/`ViewportCenter`.

## 4. Как довести превью до уровня Photoshop — итоговый принцип и порядок работ

Общий принцип, которого сейчас не хватает и который объясняет все три бага сразу: **экран никогда не должен показывать «ничего»/чёрное — он должен показывать наилучшее из того, что уже есть, пока не готово точное**. Это и есть суть «Photoshop-level» — там при зуме/скролле вы никогда не видите пустоты, в худшем случае видите слегка размазанную (растянутую с более грубого уровня) версию картинки.

Порядок фиксов по влиянию на ощущение:

1. **Фикс §1 (dirty → отдавать стейл-байты, не 202)** — устраняет прямую причину чёрных прямоугольников, наибольший эффект при наименьшем риске (это откат к уже согласованному и один раз спроектированному поведению, не новая архитектура).
2. **Фикс §3 (убрать/сузить `clear_all()`)** — устраняет мерцание, тоже низкий риск, чистое удаление вредного кода.
3. **Фикс §2 (единый источник visible-tiles + синхронизация debounce)** — устраняет рассинхрон координат, требует небольшого изменения контракта (`SetViewportResponse`), но не архитектурной перестройки.
4. **Интеграция пирамиды (`Pyramid forced level 0`, TODO из §12.3)** — это уже отмечено как известное ограничение, и стоит явно связать с текущим багом: пока zoom-out работает через рендеринг тайлов **уровня 0** с последующим сжатием на canvas, а не через реально уменьшенные тайлы верхних уровней пирамиды, при отдалении нужно **больше** тайлов полного разрешения для покрытия того же экрана — это прямое давление на 256 MB бюджет кеша и на scheduler, что дополнительно объясняет, почему именно при переключении zoom-режимов (а не в статике) чаще возникают дыры: система в моменте пытается прокормить больше данных, чем стационарно необходимо. Включение реальной пирамиды не только «фича на будущее», а прямое снижение нагрузки, вызывающей текущий баг.
5. **LOD-fallback при отрисовке (после п.4).** Как только пирамида реально работает: если точный тайл `(level, x, y)` ещё не готов, но в кеше есть **тайл родительского уровня**, покрывающий ту же область — отрисовать его растянутым как временную замену вместо чёрного/старого-того-же-уровня. Это уже чисто фронтенд-логика в `TileCanvas`/`tileWorker.ts`: при получении 202 или отсутствии данных — спросить `tile://.../l/{level+1}/{x/2}/{y/2}` как fallback, нарисовать растянутым, и заменить, когда придёт `tile-ready` точного уровня.

Пункты 1–3 — это баг-фиксы существующего кода, можно и нужно делать сразу и независимо от остального. Пункт 4 — ранее отложенный TODO, но теперь становится приоритетным, потому что напрямую снижает частоту багов 1/3, а не только даёт красивый зум. Пункт 5 — финальный штрих, который и даёт то самое «никогда не пусто», но осмыслен только после пункта 4.
