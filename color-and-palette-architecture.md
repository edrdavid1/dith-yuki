# Архитектура цвета и палитр (engine-color + палитровые фильтры)

> **Статус:** миграционный / исторический дизайн-док. Актуальное as-built поведение Color Lab, auto-extract, builtins, OkLCH/ramps/harmony и IPC — в [`COLOR_AND_COLOR_LAB.md`](./COLOR_AND_COLOR_LAB.md); обзор крейта — в `ARCHITECTURE.md` §4.3 / §9. План фич — `.cursor-spec/`.

Закрывает отложенный блок «Phase 5 / engine-color stub» из плана и §5 ТЗ. Материал из присланного кода прошлой версии (Bayer, error diffusion, Oklab, KD-tree, палитровые source/quantize ноды) — хорошая, рабочая математика, её почти всю можно переиспользовать. Проблема не в алгоритмах, а в том, что прошлая версия построена вокруг **графа нод с неявной передачей параметров upstream** (`with_current_upstream_params`), а текущая архитектура — вокруг **дерева слоёв с явным стеком `FilterInstance`** (`tile-engine-architecture.md`, `tauri-api-document-model.md`). Ниже — как перенести математику, поправив архитектурные швы.

## 1. Два цветовых пространства — и где именно граница между ними

Важно развести два разных «цвета» в системе, которые в присланном коде смешаны в одном модуле:

| Пространство | Где живёт | Зачем |
|---|---|---|
| **Linear RGB (f32)** | Постоянное хранилище — `PixelTile` во всех стадиях (`Raw`/`Processed`/`Composite`) | Уже зафиксировано архитектурой (`tile-engine-architecture.md` §2.1): все обычные фильтры (Curves, Levels, blend-моды) работают тут |
| **Oklab (f32)** | Временный буфер **только внутри** одного вызова фильтра квантизации, не хранится нигде за пределами этого вызова | Перцептивно равномерное пространство, нужно только для двух вещей: (1) поиск ближайшего цвета палитры, (2) диффузия ошибки квантизации |

### 1.1 Важная ошибка, которую нельзя унаследовать из старого кода как есть

В присланном коде `linearize()` (sRGB → linear) вызывается перед переходом в LMS/Oklab:

```rust
fn linearize(v: f32) -> f32 {
    if v <= 0.04045 { v / 12.92 } else { ((v + 0.055) / 1.055).powf(2.4) }
}
```

Это верно, **если вход — sRGB-гамма-кодированные байты** (как это было в прошлой версии, где, судя по всему, пиксели хранились в exported/наивном RGB u8). В новой архитектуре `PixelTile` **уже хранит линейный RGB f32** (решение из `tile-engine-architecture.md` §2.1 и подтверждено в первом документе про цвет: «внутреннее представление пикселей: линейное RGB»). Значит при переносе кода **шаг `linearize()` перед переходом в LMS нужно выбросить** — вызывать его повторно на уже линейных данных даст двойное degamma-искажение (пересвеченные тени, смещённый нейтральный серый). Это единственное, что нельзя копировать один в один; сам LMS/Oklab-матрицы и cube root — переносятся без изменений.

```rust
// Было (для sRGB u8 источника):
let lin = Rgb { r: linearize(r), g: linearize(g), b: linearize(b) };

// Стало (источник уже linear RGB f32 из PixelTile):
let lin = Rgb { r, g, b }; // никакого linearize() — уже линейно
```

### 1.2 Открытый вопрос на будущее: не-sRGB рабочие гаммуты

Матрица linear-RGB→LMS в присланном коде — стандартная Björn Ottosson'овская матрица, откалиброванная под **sRGB/Rec.709 primaries**. ТЗ (п. 3.1) также допускает Rec.2020. Если рабочее пространство документа — Rec.2020 (через ICC-профиль), эта матрица технически не совсем корректна (другие primaries → другая матрица RGB→LMS). Для MVP предлагаю осознанно зафиксировать: Oklab-квантизация всегда считается через промежуточную конвертацию в **linear sRGB primaries** (через уже имеющийся `lcms2`-пайплайн ICC-профилей, если рабочее пространство иное), а не пытаться иметь отдельную матрицу под каждый гаммут. Это ограничение, а не баг — стоит явно задокументировать в коде рядом с матрицей, чтобы через полгода кто-то не «оптимизировал» это в сторону тихого использования сырых primaries документа.

## 2. Палитра как сущность документа (не implicit upstream-параметр)

### 2.1 Ключевое архитектурное упрощение относительно прошлой версии

В присланном коде палитра передаётся между нодами через `with_current_upstream_params` — `PaletteSourceNode` кладёт JSON строку в свои параметры, `OklabQuantizeNode` читает upstream params в поисках `palette_json`, с fallback на собственное поле. Это разумно для **графа с ветвлением** (несколько источников палитры, переключаемых на лету), но в текущей модели документа (дерево `Layer`/`LayerGroup`, линейный стек `FilterInstance` на слое — без графа с произвольными связями между слоями) это лишний слой косвенности. Правильный аналог здесь проще:

```rust
pub struct Document {
    // ...
    pub palettes: Vec<Palette>,  // уже было заявлено как Vec<PaletteId> — теперь сама Palette тоже описываем
}

pub struct Palette {
    pub id: PaletteId,
    pub name: String,
    pub colors: Vec<LinearColor>,   // хранится в linear RGB — той же системе, что и PixelTile
    pub revision: u64,               // для инвалидации KD-tree кеша, см. §3
}

pub struct LinearColor { pub r: f32, pub g: f32, pub b: f32 }
```

Фильтр квантизации **явно** ссылается на `PaletteId`, никакого «поиска по графу вверх»:

```rust
pub enum FilterParams {
    // ...существующие Curves/Levels/Dither/Glitch...
    PaletteQuantize {
        palette_id: PaletteId,
        dither: DitherKernel,       // None | Bayer{size} | ErrorDiffusion{kernel} | CustomThresholdMap{path}
    },
}
```

Если в будущем понадобится реальный узел-источник палитры с динамическим пересчётом (например, «генерировать палитру из содержимого слоя X» и тут же квантовать другим слоем) — это уже не про архитектуру фильтров слоя, а отдельная фича «сгенерировать `Palette` и положить в `Document::palettes`», что уже спроектировано отдельной командой `generate_palette_from_layer` (`tauri-api-document-model.md` §4.4). Явная ссылка по ID проще, детерминированнее и не требует протаскивать skip-graph-lookup логику через каждый вызов фильтра.

### 2.2 Импорт/экспорт форматов

Из ТЗ: `.ase, .aco, .gpl, .pal, .csv, .json`. В присланном коде уже виден паттерн `source: "inline"/"file_gpl"/"file_hex"/"file_png"/"builtin"` — этот enum разумно перенести почти как есть, только результатом парсинга сразу является `Palette` (linear RGB), а не отложенный до квантизации JSON:

```rust
pub enum PaletteSource {
    Inline(Vec<(u8, u8, u8)>),
    File { path: PathBuf, format: PaletteFileFormat },
    Builtin(BuiltinPaletteId), // default_8, default_16, ...
    GeneratedFromLayer { layer_id: LayerId, method: PaletteGenMethod, color_count: u8 },
}

pub enum PaletteFileFormat { Ase, Aco, Gpl, Pal, Csv, Json, Png /* threshold map — см. §4 */ }
```

Парсеры каждого формата — отдельные, узкие функции `fn parse_gpl(bytes: &[u8]) -> Result<Vec<(u8,u8,u8)>, PaletteError>` и т.п., без общей магии — детали кодеков сюда не включаю намеренно (это уровень реализации, не архитектуры), но структура каталога:

```
crates/engine-color/src/palette/
  mod.rs
  ase.rs
  aco.rs
  gpl.rs
  pal.rs
  csv_json.rs
  generate.rs   // median cut, k-means — из ТЗ п. 3.4
```

## 3. KD-tree: кеш переносится на уровень палитры, а не фильтра

### 3.1 Проблема прошлого подхода в новых условиях конкурентности

В присланном коде KD-tree кешируется **внутри ноды**: `Mutex<Option<KdTree>>` + `Mutex<palette_hash>` как поля `OklabQuantizeNode`. В прошлой (видимо, однопоточной или слабо параллельной) архитектуре это нормально. В текущей — тайлы одного и того же `FilterInstance` считаются **параллельно N worker-потоками рейона** (`tile-engine-architecture.md` §5.2: приоритетная очередь, множество воркеров разбирают тайлы одного и того же документа одновременно). Если `FilterInstance` хранит `Mutex<Option<KdTree>>` как своё поле, все воркеры, обрабатывающие разные тайлы того же слоя, будут сериализовываться на этом одном `Mutex` при каждом обращении к дереву — это узкое место именно там, где параллелизм важнее всего (KD-tree поиск на тайл вызывается multiple times, по разу на пиксель).

### 3.2 Фикс: глобальный кеш `PaletteId → Arc<KdTree>`, консистентный со стилем остальной архитектуры

По аналогии с `TileCache`/`GenerationTracker` (уже `DashMap`-based, лок-фри):

```rust
pub struct PaletteKdCache {
    entries: DashMap<PaletteId, (u64 /* revision */, Arc<KdTree>)>,
}

impl PaletteKdCache {
    pub fn get_or_build(&self, palette: &Palette) -> Arc<KdTree> {
        if let Some(entry) = self.entries.get(&palette.id) {
            if entry.0 == palette.revision {
                return entry.1.clone(); // O(1) Arc clone, lock-free чтение из DashMap-шарда
            }
        }
        let tree = Arc::new(KdTree::build(&palette.colors));
        self.entries.insert(palette.id, (palette.revision, tree.clone()));
        tree
    }
}
```

`revision` вместо hash палитры (как в присланном коде — там `hash_palette`) — потому что `Palette` уже живёт внутри `Document`, у которого есть механизм `revision`/`generation`; переиспользуем тот же принцип, а не отдельное хеширование содержимого на каждый вызов (хеш N цветов на каждый тайл — лишняя работа, если можно просто сравнить целое число).

`PaletteKdCache` живёт в `AppState` рядом с `TileCache`, не внутри `FilterInstance` — один физический KD-tree на палитру, используемый всеми слоями/тайлами, которые на неё ссылаются, вместо потенциально N копий по числу фильтров, использующих одну и ту же палитру.

## 4. Dither/PaletteQuantize как фильтры тайлового пайплайна

### 4.1 Что уже правильно спроектировано в присланном коде — переносить как есть

- **Глобальные координаты для Bayer/threshold-map** (`div_euclid`/`rem_euclid` от `tile_coord.global_x/global_y`) — это ровно та же идея бесшовности между тайлами, что уже заложена в тайловый движок. `TileCoord` в новой архитектуре не хранит `global_x/global_y` явно, но они тривиально вычисляются: `global_x = coord.x * TILE_SIZE` (с поправкой на `level`, если применяется к неполноразрешению — для дизеринга это обычно не нужно, он применяется на уровне 0). Здесь не требуется halo вообще — Bayer/threshold-map не диффузионные, каждый пиксель независим, значит и швов без halo не будет, если только координаты глобальные, что уже решено.
- **Клэмп Oklab-координат** для защиты от drift/backtracking взрыва в KD-tree — переносится без изменений, это универсальная защита, не зависящая от того, откуда пришли L/A/B.
- **Обобщённые ядра диффузии** (`(dx, dy, num, den)` таблицы для Floyd-Steinberg/Atkinson) — переносятся как есть, они уже в удобной табличной форме, легко добавить новые ядра (Jarvis-Judice-Ninke, Stucki и т.п.) без изменения алгоритма применения.

### 4.2 Что нужно адаптировать под halo/tile-граничную модель

Ошибочная диффузия (что Floyd-Steinberg на serый/RGB, что Oklab-диффузия для палитровой квантизации) в присланном коде работает на **буфере всего тайла целиком** (`w×h` локальный `Vec`), без halo вообще — ошибка, доходящая до границы тайла, просто не распространяется дальше (`if nx >= 0 && nx < w ...`). Это **тот же самый компромисс**, что уже согласован в `tile-engine-architecture.md` §4 («диффузия ошибки урезается до конца строки/тайла») — то есть присланный код уже реализует именно то прагматичное решение, которое было спроектировано раньше, а не что-то новое. Никаких изменений тут не требуется, halo=2 из общей архитектуры для error diffusion фильтров можно оставить неиспользуемым в этом конкретном фильтре (или использовать 2px halo как «мягкую» границу — взять исходные, недиффузные значения соседнего тайла как контекст без переноса ошибки через границу — небольшое качественное улучшение, но не обязательное).

`requires_full_row` (флаг из `FilterInstance`, `tile-engine-architecture.md` §4) — для Dither/PaletteQuantize остаётся `false`: диффузия внутри тайла с урезанием на границе — это ровно тот случай, для которого флаг был придуман как *не*-исключение (в отличие от построчного глитча/pixel sorting, которым нужен весь документ целиком).

### 4.3 Единый или раздельный `FilterKind` для Dither и PaletteQuantize?

В присланном коде это два разных нода (`DitherNode` — Bayer/threshold/error-diffusion в RGB/grayscale без палитры, просто квантование по уровням; `OklabQuantizeNode` — квантование к конкретной палитре в Oklab). Предлагаю сохранить это разделение и в `FilterKind`, а не сливать в один мега-фильтр с десятком опциональных полей:

```rust
pub enum FilterKind {
    Curves,
    Levels,
    Dither,           // Bayer / Ordered / Threshold / error-diffusion БЕЗ конкретной палитры — просто N уровней на канал
    PaletteQuantize,  // квантование к конкретной Palette через Oklab + KD-tree, с опциональной диффузией
    Glitch,
}
```

Обоснование: `Dither` без палитры (просто «N уровней серого/RGB») и `PaletteQuantize` (конкретный набор цветов) — разные операции с разными параметрами и разной механикой (одной не нужен KD-tree и Oklab вообще, зачем тащить эту машинерию туда, где квантование идёт по равномерной сетке уровней). Пользователь стека фильтров может комбинировать оба (например, сначала Levels, потом Dither для ретро-эффекта, потом отдельно PaletteQuantize для приведения к конкретной палитре — как в оригинальном ТЗ упомянуты «дизеринг» и «палитры» как разные пункты 3.1/3.4).

## 5. Custom PNG threshold map — sandbox-логика как общий принцип, не частность dither-фильтра

Секьюрити-проверки из присланного кода (только `.png`, путь обязан быть под `HOME`, `canonicalize` для разрешения symlink-побега) — это хороший паттерн, но сейчас он специфичен для одного фильтра. В новой архитектуре любой путь к внешнему файлу, приходящий как параметр (custom threshold map, палитра из файла в §2.2, в будущем — LUT-файлы для цветокоррекции) должен проходить через одну и ту же проверку, а не дублироваться в каждом месте, где параметром является путь:

```rust
// crates/engine-io/src/sandbox.rs
pub fn resolve_user_path(raw: &str, allowed_ext: &[&str]) -> Result<PathBuf, SandboxError> {
    let path = Path::new(raw);
    let ext_ok = path.extension()
        .and_then(|e| e.to_str())
        .map(|e| allowed_ext.iter().any(|a| a.eq_ignore_ascii_case(e)))
        .unwrap_or(false);
    if !ext_ok { return Err(SandboxError::BadExtension); }

    let abs = std::fs::canonicalize(path).map_err(|_| SandboxError::NotFound)?;
    let home = dirs::home_dir().ok_or(SandboxError::NoHome)?;
    if !abs.starts_with(&home) { return Err(SandboxError::OutsideHome); }
    Ok(abs)
}
```

Threshold-map-загрузчик и палитровый файловый импорт (§2.2) оба вызывают `resolve_user_path` вместо того, чтобы каждый писать свою версию этой проверки — иначе через полгода кто-то добавит третий путь-параметр и забудет про sandbox.

**Кеширование threshold map** — тот же паттерн из §3.2 (глобальный `DashMap`, не `Mutex<Option<...>>` внутри фильтра), инвалидация по пути + mtime файла, а не только по `custom_path`-строке (если пользователь заменил файл на диске тем же именем, стоит перечитать — mtime дешевле, чем хешировать содержимое картинки на каждое обращение).

## 7. Что сознательно отложено (не блокирует MVP, но стоит держать в голове)

- ICC-aware Oklab-матрица для не-sRGB рабочих пространств (§1.2) — зафиксировано как явное ограничение с комментарием в коде, не тихий баг.
- 8×8 (и больше) матрицы Байера — присланный код и предыдущая реализация используют упрощённые 2×2/4×4; расширение до произвольного размера — чисто добавление константы, не архитектурное изменение.
- Генерация палитры «на лету» из графа (динамический upstream, как в старом коде) — сознательно упрощено до explicit `PaletteId` + отдельная команда генерации (§2.1); если понадобится живой пересчёт «палитра меняется вместе с содержимым слоя-источника» — это отдельная инвалидационная цепочка (`Palette` тоже должна получить свой `generation`, и `PaletteQuantize`-фильтры, ссылающиеся на неё, должны инвалидироваться при её пересчёте) — стоит спроектировать отдельно, если эта фича реально нужна, а не добавлять реактивно.
