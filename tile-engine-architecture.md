## 1. Базовые адресные типы

Всё в системе адресуется по стабильным целочисленным ID, а не по указателям/индексам в векторах — это важно, потому что тайлы живут и умирают асинхронно, и any indices could invalidate.

```rust
/// Уникальный ID слоя, стабилен в течение жизни документа.
pub type LayerId = u32;

/// Уровень пирамиды: 0 = полное разрешение, 1 = /2, 2 = /4, ...
pub type MipLevel = u8;

/// Координаты тайла внутри одного уровня пирамиды.
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct TileCoord {
    pub level: MipLevel,
    pub x: u32,
    pub y: u32,
}

/// Полный адрес тайла: какому слою принадлежит + координаты.
/// Для композитных тайлов используется LayerId::MAX как признак "весь документ".
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct TileKey {
    pub layer: LayerId,
    pub coord: TileCoord,
    pub stage: CacheStage,
}

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub enum CacheStage {
    Raw,        // исходные пиксели слоя, без фильтров
    Processed,  // после fill/adjustment фильтров слоя + маски
    Composite,  // после наложения на нижележащие слои (blend + opacity)
}
```

Размер тайла — константа уровня приложения (256 или 512), задаётся один раз при создании документа и не меняется (миграция размера тайла = пересборка пирамиды с нуля, это дорогая офлайн-операция, не рантайм-фича).

```rust
pub const TILE_SIZE: u32 = 256;
pub const HALO: u32 = 2; // перекрытие для диффузионных фильтров, см. §5
```

## 2. Пирамида и хранение пикселей

### 2.1 Формат тайла в памяти

Внутренний пиксельный формат — линейный RGBA, `f32` на канал (см. блок «цвет» отдельно, но тип задаётся здесь, потому что он определяет размер тайла в байтах):

```rust
pub struct PixelTile {
    pub data: Box<[f32]>, // len = (TILE_SIZE + 2*HALO)^2 * 4, RGBA interleaved
}
```

256×256 тайл с гало 2px и 4 канала f32 = `260*260*4*4 байта ≈ 1.08 МБ`. При 10 слоях и полной пирамиде для 5000×5000 это даёт понимание порядка величин для §6 (память/scratch).

### 2.2 Структура пирамиды

Пирамида — не отдельная структура на слой, а **ленивая функция**: тайлы верхних уровней вычисляются понижающей дискретизацией (box-фильтр 2×2) из тайлов уровня 0 **по требованию**, и результат кешируется как обычный `Raw`-тайл этого слоя на уровне N. То есть уровень 0 — источник истины, остальные уровни — производные, живущие в том же кеше с тем же механизмом инвалидации.

```rust
pub struct Layer {
    pub id: LayerId,
    pub kind: LayerKind,
    pub blend_mode: BlendMode,
    pub opacity: f32,
    pub visible: bool,
    pub offset: (i32, i32),       // смещение слоя относительно холста
    pub mask: Option<MaskRef>,
    pub filters: Vec<FilterInstance>, // для Adjustment-слоёв; для Raster — пост-фильтры
    /// Границы слоя в тайлах уровня 0 — нужно, чтобы не запрашивать
    /// тайлы за пределами реального содержимого слоя.
    pub bounds_l0: TileBounds,
}

pub enum LayerKind {
    Raster,      // хранит Raw-тайлы уровня 0
    Adjustment,  // не хранит пиксели, только применяет filters к композиту снизу
}
```

Важное следствие: для `Adjustment`-слоя запрос `Raw`-тайла не имеет смысла — сразу запрашивается `Processed`, который берёт как вход `Composite` тайл слоёв ниже. Это единственное исключение из общего трёхуровневого кеша, и его стоит явно закодировать в типе, а не проверять `if kind == Adjustment` россыпью по кодовой базе — иначе будет вечный источник багов при добавлении новых стадий.

## 3. Трёхуровневый кеш

### 3.1 Структура кеша

```rust
pub struct TileCache {
    entries: DashMap<TileKey, CacheEntry>,
    lru: SegQueue<TileKey>,          // приближённый LRU, не строгий
    budget_bytes: AtomicUsize,
    used_bytes: AtomicUsize,
}

pub struct CacheEntry {
    pub tile: Arc<PixelTile>,
    pub generation: u64,      // см. §5 — поколение, на котором тайл посчитан
    pub last_touched: Instant,
    pub dirty: AtomicBool,    // помечен устаревшим, но ещё не пересчитан
}
```

`DashMap` — потому что чтение/запись идёт из множества worker-потоков rayon одновременно, и глобальный `Mutex<HashMap>` станет точкой сериализации при 30+ fps перерисовке.

### 3.2 Ключевое решение: инвалидация — это не удаление, а пометка `dirty`

Наивный подход «при изменении параметра фильтра удаляем все зависимые тайлы из кеша» плох тем, что:
1. на экране мгновенно появляется дыра (нечего рисовать), пока не пересчитается новый тайл;
2. при быстром скраббинге слайдера (десятки изменений в секунду) это триггерит лавину аллокаций/деаллокаций.

Вместо этого:
- Тайл остаётся в кеше и продолжает рендериться (даже устаревший — лучше показать чуть старую картинку, чем пустоту).
- Он помечается `dirty = true` и получает **старое** значение `generation`.
- Планировщик (§5) видит расхождение `entry.generation != current_generation(layer)` и ставит пересчёт в очередь.
- Когда пересчёт готов, `dirty` снимается атомарно, `generation` обновляется, старые данные тайла заменяются новыми (тот же слот в `DashMap`, без удаления ключа) — с точки зрения фронтенда это просто «тайл обновился», без мигания.

### 3.3 Инвалидация снизу вверх по графу зависимостей

Зависимости строго однонаправленные: `Raw(layer, coord) → Processed(layer, coord) → Composite(coord)`, причём `Composite(coord)` уровня L зависит от `Composite` **всех видимых слоёв ниже** в том же координатном пространстве плюс `Processed` текущего слоя. Формально:

```rust
fn invalidate(cache: &TileCache, doc: &Document, source: InvalidationEvent) {
    match source {
        InvalidationEvent::LayerRawChanged { layer, coords } => {
            for coord in coords {
                mark_dirty(cache, TileKey { layer, coord, stage: Raw });
                mark_dirty(cache, TileKey { layer, coord, stage: Processed });
                cascade_composite(cache, doc, layer, coord);
            }
        }
        InvalidationEvent::LayerFilterChanged { layer } => {
            // фильтр слоя влияет на ВСЕ тайлы этого слоя во всех мип-уровнях
            for coord in cache.keys_for_layer(layer, CacheStage::Processed) {
                mark_dirty(cache, TileKey { layer, coord, stage: Processed });
                cascade_composite(cache, doc, layer, coord);
            }
        }
        InvalidationEvent::LayerPropsChanged { layer } => {
            // opacity/blend_mode/visibility/offset — Processed не трогаем,
            // достаточно пересчитать Composite
            for coord in cache.keys_for_layer(layer, CacheStage::Processed) {
                cascade_composite(cache, doc, layer, coord);
            }
        }
        InvalidationEvent::MaskChanged { layer, coords } => {
            for coord in coords {
                mark_dirty(cache, TileKey { layer, coord, stage: Processed });
                cascade_composite(cache, doc, layer, coord);
            }
        }
    }
}

/// Composite(coord) зависит от текущего слоя и ВСЕХ слоёв выше него
/// (порядок снизу вверх), т.к. они всё ещё используют его как основу.
fn cascade_composite(cache: &TileCache, doc: &Document, changed_layer: LayerId, coord: TileCoord) {
    for layer_above_or_eq in doc.layers_from(changed_layer) {
        mark_dirty(cache, TileKey { layer: layer_above_or_eq, coord, stage: Composite });
    }
}
```

`LayerPropsChanged` (просто сдвинули opacity-слайдер) специально не трогает `Processed` — это тот случай, который должен пересчитываться за единицы миллисекунд, так как это самое частое действие пользователя.

### 3.4 Вытеснение (eviction)

LRU с бюджетом в байтах, но с одним исключением: тайлы уровня 0 в пределах **текущего вьюпорта** никогда не вытесняются, даже если `budget` превышен — иначе можно попасть в цикл «вытеснили → тут же запросили → пересчитали → вытеснили». Вытеснение при превышении бюджета идёт в порядке: сначала верхние (мелкие) уровни пирамиды *вне* вьюпорта → затем `Composite` вне вьюпорта → затем `Processed`. `Raw` тайлы уровня 0 вытесняются последними и только на диск-scratch (не удаляются насовсем — иначе пересчёт `Raster`-слоя без фильтра невозможен, это же оригинальные пиксели, не производные данные).

## 4. Обработка тайлов с перекрытием (halo) для диффузионных фильтров

Проблема: Флойд–Стейнберг дизеринг и подобные фильтры с error diffusion переносят ошибку квантования на соседние пиксели **справа и снизу**. Если тайл обрабатывать изолированно, на границе тайла ошибка обрывается — визуально это шов.

Решение — двухфазная схема:

**Фаза A (halo pass).** При запросе `Processed`-тайла бекенд на самом деле обрабатывает область `TILE_SIZE + 2*HALO` пикселей, беря `HALO` пикселей из соседних тайлов того же слоя (или из зафиксированного «состояния ошибки на границе», см. ниже). Возвращается наружу только центральная `TILE_SIZE × TILE_SIZE` область — гало используется исключительно для корректности диффузии внутри тайла и отбрасывается.

**Фаза B (border state).** Для честного Floyd–Steinberg (не приближения) двух пикселей гало недостаточно — ошибка теоретически может накапливаться сколь угодно далеко по строке. Прагматичное решение (используется большинством плиточных редакторов): диффузия ошибки **урезается до конца строки тайла** — при достижении правой границы тайла остаток ошибки просто отбрасывается, а не переносится в соседний тайл. Это даёт видимый, но контролируемый и стабильный артефакт (тонкая менее заметная граница раз в TILE_SIZE пикселей) взамен полной корректности. Обосновано тем, что:
- полная корректность требует последовательной обработки всей строки документа целиком, что убивает распараллеливание по тайлам — прямое противоречие с NFR о параллельной обработке;
- визуальная разница на TILE_SIZE=256 при типичных изображениях статистически исчезающе мала, особенно при diffusion-дизеринге с уже случайным/псевдослучайным паттерном ошибки.

Если для конкретного глитч-эффекта (например, построчный pixel sorting) нужна честная **построчная**, а не потайловая обработка — такие фильтры помечаются флагом `requires_full_row: bool` в `FilterInstance` и **не участвуют в тайловом пайплайне вообще**: они обрабатывают весь `Raw` слоя целиком в отдельном проходе перед тайлированием результата в `Processed`. Это осознанное исключение, а не попытка притянуть построчные эффекты к тайловой модели — они принципиально не тайлируемы без потери смысла эффекта.

```rust
pub struct FilterInstance {
    pub kind: FilterKind,
    pub params: FilterParams,
    pub requires_full_row: bool, // true для row-based glitch, false для dithering/color
}
```

## 5. Планировщик: поколения, приоритет, отмена

### 5.1 Generation ID — механизм отбрасывания устаревших задач

Каждое изменение параметра (слайдер двинули на 1 пиксель) увеличивает глобальный монотонный счётчик документа `doc.generation`. Задача пересчёта тайла, поставленная в очередь, несёт снимок `generation` на момент постановки:

```rust
pub struct RecomputeTask {
    pub key: TileKey,
    pub generation: u64,
    pub priority: Priority,
}
```

Перед выполнением (а не только при постановке в очередь — важно, т.к. задача могла ждать в очереди сотни миллисекунд) worker сверяет `task.generation == doc.generation.load()`. Если не совпадает — задача выбрасывается без вычислений, worker сразу переходит к следующей. Это дешёвая проверка (один atomic load), которая полностью решает проблему «пользователь дёргает слайдер быстрее, чем мы считаем» — без неё очередь бы неограниченно росла хвостом устаревшей работы.

Важный нюанс: `generation` **не глобальный для всего документа при локальных изменениях**. Если меняется только один слой, незачем инвалидировать generation-проверку задач для тайлов, вообще не зависящих от этого слоя — иначе безобидное изменение одного corner-слоя отменит вычисления, идущие для соседнего независимого слоя. Поэтому реально используется двухуровневая схема:

```rust
pub struct GenerationTracker {
    pub document_gen: AtomicU64,             // растёт всегда
    pub layer_gen: DashMap<LayerId, u64>,     // растёт при изменении конкретного слоя
}
```

Задача несёт оба значения; актуальность проверяется только по тому уровню, который реально релевантен стадии (`Processed(layer)` сверяется с `layer_gen[layer]`, `Composite` — с максимумом `layer_gen` по всем слоям на/ниже него, `document_gen` используется только для полной отмены при закрытии/переоткрытии документа).

### 5.2 Приоритетная очередь

```rust
#[derive(PartialEq, Eq, PartialOrd, Ord)]
pub enum Priority {
    Immediate,     // грубый (низший непустой) уровень пирамиды текущего вьюпорта
    ViewportCenter,
    ViewportEdge,
    Prefetch,      // за пределами вьюпорта, для плавного панорамирования
}
```

Очередь — не одна `BinaryHeap`, а `rayon`-совместимый пул с `crossbeam::channel` из 4 приоритетных бакетов; worker всегда сначала опустошает `Immediate`, затем остальные. Это проще и предсказуемее по латентности, чем честная приоритетная куча с миллионами re-heapify при постоянной вставке/отмене.

Поток «мгновенной обратной связи» (п. 5.3 ТЗ) выглядит так:

1. Параметр меняется → `layer_gen[layer] += 1`.
2. Синхронно (в том же кадре, без похода в очередь) пересчитывается **самый грубый непустой уровень пирамиды**, покрывающий текущий вьюпорт — обычно это 1–4 тайла размером с весь экран после downsample, счёт идёт на десятки-сотни микросекунд на f32-буфере такого масштаба. Результат сразу отдаётся на фронт как «черновой» кадр.
3. Параллельно в `Immediate`/`ViewportCenter` бакеты кладутся задачи на полное разрешение видимых тайлов, отсортированные по манхэттенскому расстоянию до центра вьюпорта.
4. По мере готовности каждого тайла — событие фронту «тайл (x,y,level) обновлён», фронт заменяет черновой блок на точный без перерисовки всего холста.
5. `ViewportEdge`/`Prefetch` заполняют соседние тайлы фоном для плавного панорамирования — не блокируют основной поток.

### 5.3 Отмена «на лету»

`rayon` не поддерживает кооперативную отмену задач из коробки, поэтому отмена — не «убийство» потока, а тот же чек `generation` в начале функции обработки тайла **плюс** периодическая проверка внутри длинных фильтров (например, честный k-means на палитре или тяжёлый LUT-пересчёт) каждые N итераций — чтобы не тратить 5 мс на заведомо ненужный результат, даже если проверка на входе уже была пройдена, но за время работы поколение успело смениться.

## 6. Композитинг: проход по тайлу

```rust
fn composite_tile(doc: &Document, coord: TileCoord, cache: &TileCache) -> PixelTile {
    let mut accum = PixelTile::transparent();
    for layer in doc.layers_bottom_to_top() {
        if !layer.visible || layer.opacity == 0.0 { continue; }
        if !layer.bounds_l0.contains(coord) { continue; } // экономим — не трогаем несуществующие тайлы

        let processed = cache.get_or_schedule(TileKey { layer: layer.id, coord, stage: Processed });
        let masked = apply_mask(processed, layer.mask.as_ref(), coord);
        blend_onto(&mut accum, &masked, layer.blend_mode, layer.opacity);
    }
    accum
}
```

`get_or_schedule` — если тайл в кеше и не `dirty`, возвращает сразу; если `dirty` или отсутствует — возвращает **последнее известное значение** (или прозрачный тайл, если данных вообще не было) и одновременно ставит задачу пересчёта в очередь с нужным приоритетом. Это то самое место, где «неточная, но мгновенная» картинка превращается в «точную с небольшой задержкой» без блокировки текущего кадра рендера.
