## 0. Единственный открытый вопрос — закрыть первым, до остального кода

### Spike: popout в контексте Tauri, не браузера

**Проблема:** FlexLayout реализует popout-окна через React Portals поверх
`window.open()` — это браузерный API. Приложение работает внутри Tauri
WebView, не в обычном браузере. Неизвестно заранее, создаст ли
`window.open()` внутри Tauri WebView настоящее нативное окно, или
потребуется мост поверх Tauri's `WebviewWindowBuilder`.

**Что сделать до начала B3:**
1. Минимальный прототип (вне основного кода, отдельная ветка/scratch):
   один `<Layout>` с одной панелью, вызвать popout, проверить в реальном
   Tauri-приложении (не `tauri dev` в браузерной вкладке — обязательно
   собранное desktop-окружение на всех целевых ОС, minimum macOS раз это
   основная платформа разработки).
2. Три возможных исхода, зафиксировать какой именно:
   - **(a) Работает нативно** — Tauri настроен так, что `window.open()`
     создаёт полноценное OS-окно без доп. работы. Тогда ничего не нужно
     делать, FlexLayout popout используется как есть.
   - **(b) Не работает / открывает не то, что нужно** (например, ничего
     не происходит, или открывается в системном браузере вместо
     нативного окна) — нужен мост: перехватить FlexLayout popout API
     (`onCreateTabSet`/render callbacks, где есть точка расширения —
     смотреть актуальную popout-документацию FlexLayout для версии
     0.10.x) и внутри него вызывать `WebviewWindowBuilder` от Tauri
     вместо стандартного `window.open`.
   - **(c) Частично работает, но с существенными огрехами** (например,
     не прокидываются Tauri IPC-каналы в новое окно, стили не
     подгружаются) — то же решение, что (b), плюс список конкретных
     доработок моста.
3. Результат spike — короткая заметка (`POPOUT_SPIKE.md`) с исходом (a),
   (b) или (c) и, если (b)/(c), с планом моста. **Это блокер для B3**,
   если требуется popout — не начинать миграцию панелей, пока не ясно,
   как будет работать popout, иначе рискуете мигрировать всё, а потом
   узнать, что нужно переделывать интеграцию с нуля.

**Если TileCanvas polling/IPC уже показывал похожие проблемы с
браузерными API внутри WebView** (стоит свериться с фронтенд-командой,
были ли уже похожие грабли) — использовать этот опыт как стартовую точку
догадки об исходе (a)/(b)/(c), не гадать с нуля.

## 1. Архитектурное решение: кто владеет состоянием layout

**Меняется владелец истины.** Сейчас — `PanelManager` (Rust), после
миграции — **FlexLayout `Model`** (JS/TS, в памяти фронтенда).

```
ДО:
  Rust PanelManager (source of truth)
    → emit panel-state-changed → React re-render (просто зеркало)

ПОСЛЕ:
  FlexLayout Model (source of truth, в React state)
    → сериализация в JSON при изменении → Tauri command → диск
    → Rust НЕ принимает решений о layout, только хранит и отдаёт байты
```

**Явное следствие:** Rust-сторона (`panel_manager.rs`) перестаёт быть
state machine и становится **тонким persistence-слоем**: принимает JSON
от фронтенда, пишет на диск, отдаёт JSON при старте. Никакой геометрии,
никакого dock/undock decision-making в Rust после миграции.

**Не пытаться сохранить `PanelManager` API "для совместимости"** —
дуальный источник истины (одновременно Rust state machine и FlexLayout
Model) — это худший из вариантов, гарантированная рассинхронизация.
Полная замена роли, не постепенное сосуществование двух систем принятия
решений.

## 2. Судьба каждого файла из аудита (явно, чтобы не гадать)

| Файл | Судьба |
|------|--------|
| `dock_affinity.rs` | **Удалить целиком** после миграции. Hit-test/hysteresis-геометрия — теперь внутри FlexLayout, не переносить логику, библиотека решает это сама. |
| `panel_manager.rs` | **Переписать в тонкий persistence-слой.** Убрать geometry/decision-логику (`undock_panel` geometry, `dock_panel_at` insert-index и т.д.). Оставить только: принять JSON layout от фронтенда → записать на диск; прочитать JSON с диска → отдать фронтенду при старте. |
| `global_mouseup.rs` | **Удалить целиком.** FlexLayout использует обычные browser drag events внутри одной WebView — не нужен platform-specific NSEvent/GetAsyncKeyState код. Это же закрывает "Linux не поддерживается" из аудита — бесплатно, как следствие архитектуры, не отдельная задача. |
| `commands/panels.rs` (15 команд) | **Сократить до 2-3 команд:** `save_layout(json: String)`, `load_layout() -> String`, опционально `reset_layout_to_default()`. Все geometry/drag/dock-affinity команды (`begin_float_drag`, `poll_panel_affinity`, `update_dock_zone`, `dock_panel_at`, `move_panel_to_side`, `swap_sidebars` и т.д.) — удалить, эта логика теперь внутри FlexLayout на фронтенде. |
| `panel_persistence.rs` | **Адаптировать под новую схему** (см. §3 ниже), логика graceful degradation (файл не найден/corrupt → дефолт) — сохранить как есть, это не специфично для старой системы. |
| `services/panel_service.rs` | **Удалить**, если это была обёртка исключительно вокруг удаляемых операций `PanelManager`. Проверить на использование где-то ещё перед удалением. |
| `src/shared/ipc/events.ts` | Убрать listeners на `dock-affinity` (не нужен, нет больше affinity-механики). `panel-state-changed` — заменить на простой save-on-change из FlexLayout `onModelChange`. |

## 3. Persistence: схема v3 и миграция с v2

**Не пытаться транслировать v2 JSON (`PanelManager` формат) в FlexLayout
Model программно с сохранением точного layout пользователя.** Структуры
принципиально разные (v2 — плоские `left_order`/`right_order` с
`dock_side`; FlexLayout Model — дерево `RowNode`/`TabSetNode`/`TabNode`).
Попытка точного 1:1 маппинга — источник тонких багов, не стоит усилий
ради сохранения layout, который пользователь может пересобрать за 10
секунд.

**Решение:** при обнаружении v2-файла на диске — **не мигрировать,
использовать дефолтный FlexLayout layout** (аналог текущего дефолта:
layers/colorlab слева или справа, как было "из коробки" в v1→v2
миграции). Один раз показать уведомление/toast "Layout был сброшен к
стандартному после обновления" — честно, не молча.

**Формат v3:** ровно то, что отдаёт `Model.toJson()` из FlexLayout,
плюс обёртка с версией:

```json
{
  "version": 3,
  "flexlayout_model": { /* Model.toJson() as-is */ }
}
```

Не пытаться augментировать/кастомизировать формат — минимальная
обёртка, максимум доверия к тому, что библиотека сама умеет
сериализовать и десериализовать корректно.

## 4. Явные решения по вопросам, оставленным открытыми в аудите

### 4.1 Nested floating-in-floating

**Решение: разрешить**, не ограничивать искусственно. Аудит пометил
текущее отсутствие этой возможности как "нормально для дизайна", но это
было следствием ограничений старой архитектуры (два отдельных OS-окна),
не продуктовым требованием. FlexLayout поддерживает это естественно —
не тратить время на код, который специально это запрещает.

**Если после B3-прототипа окажется, что nested floating создаёт
путаницу в UX** — тогда это отдельное продуктовое решение по данным
использования, не архитектурное ограничение, зашитое заранее без
причины.

### 4.2 `last_dock_sides` (память "куда panel возвращалась в последний раз")

**Решение: не переносить отдельным механизмом.** FlexLayout Model уже
хранит полное дерево layout в любой момент — "последняя позиция" панели
это её текущая позиция в дереве до undock, что модель и так знает через
свою внутреннюю структуру. Отдельная in-memory карта `last_dock_sides`
избыточна поверх того, что уже даёт библиотека.

### 4.3 Drag-to-reorder внутри sidebar и snap/resize между панелями

**Решение: получаем бесплатно от библиотеки**, не реализуем сами — это
были явные пробелы старой системы (аудит §"Что текущая реализация
делает плохо", пункты 1-2), FlexLayout поддерживает оба из коробки.
Явных доп. задач не заводить — это не отдельная фича, это часть
базового поведения библиотеки, которая появится сама после миграции
компонента.

### 4.4 Второй монитор / явный popout

Закрывается тем же механизмом, что и B7 из канбана — FlexLayout popout
(после решения по §0 spike). Отдельно реализовывать "Open in new
window" вручную не нужно, если FlexLayout popout API уже даёт эту
возможность как штатную функцию — обернуть в понятный UI-жест (кнопка/
пункт меню на панели), не более того.

## 5. Операционные нюансы FlexLayout — куда именно они попадают в коде

Из документации библиотеки, зафиксировать как известные ограничения,
не открытия "в проде":

| Нюанс | Что сделать |
|-------|-------------|
| Таймеры троттлятся в фоновом popout-окне | Если в панели есть что-то time-sensitive (нет очевидных кандидатов среди текущих панелей — `effect`, `layers`, `colorlab`, `preview`, `preferences` — но перепроверить при миграции `preview`, если она получит popout) — использовать Web Worker, не `setInterval`/`setTimeout` впрямую. |
| Event listeners вешать на `document` конкретного popout-окна | Ревью-чеклист для B4: любой компонент, слушающий глобальные DOM-события (resize, keydown и т.п.), должен получать правильный `document` через FlexLayout API, не глобальный `window.document` по умолчанию. |
| Popout не масштабируется корректно при browser zoom | Не блокер, но занести в известные ограничения UI (аналогично тому, как в других отчётах фиксировались "known limitations", а не молчаливые дыры). |
| Popout не может быть восстановлен в maximized/minimized состоянии | Так же — известное ограничение, задокументировать, не пытаться обойти в первой итерации. |
| State сохраняется между окнами, но `enableWindowReMount` доступен для форсирования ремонта | Использовать `enableWindowReMount` только если конкретная панель покажет проблемы с сохранением React state при popout/dock обратно — не включать превентивно на все панели без причины. |

## 6. Non-goals этого ADR (явно, чтобы не расширялось "заодно")

- Не переделывать содержимое самих панелей (`effect`, `layers`,
  `colorlab`, `preview`, `preferences`) — только контейнер/layout вокруг
  них.
- Не менять `floating_only` статус `preview`/`preferences` без отдельного
  продуктового решения — они остаются не-докуемыми, если не появится
  явная причина это менять.
- Не реализовывать persistence per-document (layout привязан к
  приложению в целом, не к открытому файлу) — если это понадобится
  позже, отдельный ADR, не часть B2.
- Не оптимизировать bundle size / lazy-loading FlexLayout в этой фазе —
  сначала корректность миграции, оптимизация — отдельная задача при
  необходимости.
