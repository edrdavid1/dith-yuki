# GPU-resident архитектура — план построения с нуля правильно

Решение принято: не патчить v1, строить Path B (GPU-resident image,
compute graph) как основную архитектуру. Этот документ — не список
пожеланий, а последовательность с проверяемыми критериями на каждом шаге.
"Правильно" не означает "без фаз" — фазы здесь не компромисс, а
единственный способ не оказаться через 4 месяца без работающего продукта.

**Нерушимое условие на весь путь:** CPU-путь остаётся живым и является
source of truth до тех пор, пока GPU-путь не пройдёт benchmark gate на
реальных пресетах. Это не "путь A как заглушка" — это страховка. Убрать
её — значит рисковать продуктом ради архитектурной чистоты, что и есть
классическая ошибка "правильной архитектуры", остановившей проект
на середине.

---

## Фаза 0 — Контракты, до единой строчки compute-кода

Это самая важная фаза и самая дешёвая для ошибки, если пропустить.
Решения здесь фиксируют форму всего, что строится дальше — переделать
их после Фазы 2 будет дороже, чем весь Path A вместе взятый.

### 0.1 Формат GPU-resident тайла

- Texture format: `rgba32f` (соответствует текущему CPU `PixelTile` f32) —
  или сознательный переход на `rgba16f` для экономии VRAM с задокументированным
  влиянием на parity-бюджет (`≤ 1/255` сейчас рассчитан для f32 CPU
  reference; f16 меняет допуски, нужно пересчитать).
- Halo: тайл на GPU — 260×260 (как CPU `PixelTile`) с тем же halo=2px,
  или переход на atlas с явными border-тайлами вместо halo-дублирования?
  **Решить сейчас** — оба варианта валидны, но halo-подход совместим с
  текущим `GlobalCoord`/`compute_processed_tile` контрактом почти без
  изменений; atlas без halo дешевле по памяти, но требует переписать
  border-handling во всех фильтрах заново.
- **Рекомендация:** сохранить halo-модель на первой итерации — совместимость
  с существующим `GlobalCoord::from_local_with_halo` контрактом снижает
  риск рассинхронизации CPU/GPU реализаций одного и того же фильтра.

### 0.2 Layout: texture array vs sparse atlas

- Texture array (fixed slots, N тайлов) — проще реализовать, проще
  eviction (LRU по слотам), но верхний предел числа GPU-resident тайлов
  фиксирован заранее.
- Sparse/virtual texture atlas — гибче, ближе к тому, что делает Photoshop,
  сложнее реализовать правильно (свой allocator поверх GPU memory).
- **Рекомендация для первой итерации:** texture array с фиксированным
  бюджетом слотов (аналог текущего `TileCache` 512 MiB, но на VRAM,
  отдельным числом — VRAM обычно меньше системной RAM, бюджет должен
  быть отдельным параметром, не переиспользовать 512 MiB как есть).

### 0.3 Interplay с multi-doc cache budget (уже существующей системой)

GPU-resident cache становится **третьим ярусом** памяти поверх уже
спроектированной двухъярусной модели (`multi-doc-cache-budget` — CPU RAM
budget + Raw hard-pin для открытых документов):

```
GPU VRAM (новый ярус, горячий)
   ↓ eviction
CPU RAM TileCache (существующий, 512 MiB budget)
   ↓ eviction (Raw open docs hard-pinned — уже есть)
Disk / re-decode (существующий fallback)
```

**Решить сейчас:** правило eviction между VRAM и RAM должно использовать
тот же `EvictContext` (active_doc, open_docs, viewport_coords), что уже
реализован для CPU-яруса — не изобретать вторую независимую политику.
GPU-ярус — просто ещё один `CacheStage`-подобный уровень с тем же
doc-aware приоритетом вытеснения, который вы уже построили и оттестировали.

### 0.4 Compute graph IR

Что такое "граф" технически — решить до кода:
- Узел = один фильтр (тот же порядок, что сейчас в CPU `FilterStack`)?
- Или узел = один compute pass, а один фильтр может разворачиваться в
  несколько pass (например, Bayer = 1 pass, но Guided quantize + snap = 2
  pass)?
- **Рекомендация:** 1:1 маппинг CPU `FilterStack` entry → один или
  несколько GPU pass, но граф в целом строится **из того же списка
  фильтров слоя**, что и сейчас — не параллельная модель стека, которая
  может разойтись с CPU-версией по семантике/порядку.

### 0.5 Критерий готовности Фазы 0

Документ (ADR), не код: зафиксированы 0.1–0.4, ревью пройдено, никто не
пишет shader/dispatch код до этого пункта.

## Фаза 1 — Один документ, один фильтр, полный вертикальный срез

**Цель:** доказать, что вся цепочка Raw(GPU) → compute → Composite(GPU) →
readback → экран работает end-to-end, на **одном** самом простом фильтре
(Bayer4×4, без палитры, без pixel_size>1 — тот же eligibility, что уже
есть в v1). Не расширять breadth фильтров, пока этот срез не доказан.

**Объём:**
- GPU-resident tile cache (0.1–0.3) для одного документа, один слой.
- Compute graph из Фазы 0.4, но граф из одного узла (Bayer).
- Display: **простой readback раз на кадр** (не per-filter, не B5
  нативный surface — это отдельный трек, не блокирует Фазу 1). Один
  download на весь видимый composite, не 40 round-trip на 40 тайлов, как
  в текущем v1 — вот тут уже виден архитектурный выигрыш даже на одном
  фильтре.
- CPU-путь остаётся активным и является тем, что реально показывается
  пользователю, пока GPU-путь не пройдёт критерий готовности ниже.

**Критерий готовности:**
1. Pixel-parity тест Bayer GPU-resident vs CPU reference — bit-exact
   (тот же бюджет, что уже есть для v1 Bayer).
2. Benchmark на реальном viewport (~40 тайлов, origin 100%, far-corner)
   — GPU-resident путь быстрее CPU-пула **и** быстрее текущего v1
   per-tile GPU. Если не быстрее — где-то в 0.1–0.4 принято неверное
   решение, возвращаться в Фазу 0, не патчить Фазу 1 точечно.
3. Eviction между VRAM/RAM ярусами не ломает generation/staleness
   инвариант (тот же тест-класс, что TICKET-1 — GPU-тайл, вытесненный
   под pressure и позже перезапрошенный, не должен вернуть stale
   generation).

Пока пункт 2 не выполнен — **не двигаться в Фазу 2**. Это самая частая
причина, по которой "правильная архитектура сразу" превращается в
незаконченный долгострой: расширение breadth до того, как доказан
фундамент, распыляет работу по некорректному основанию.

## Фаза 2 — Расширение breadth: pattern-фильтры + palette

**Только после Фазы 1 пройдена целиком.**

- Добавить в граф: Halftone, CRT (те же три, что в текущем v1
  eligibility — не изобретать новые категории раньше времени).
- Добавить palette-constrained dither (Strict/Guided/Mixed) через
  `PaletteLut3D` как 3D-текстуру (см. предыдущее сообщение — технически
  проще, чем bias/angle для Bayer).
- Расширить eligibility: `threshold_bias`, `pattern_angle` для Bayer —
  на GPU-resident графе это дешевле добавить, чем было в v1 (не нужно
  переделывать per-tile dispatch, только добавить uniform-параметры и
  ветвление в шейдере).

**Критерий готовности:** каждый добавленный фильтр проходит тот же
parity + benchmark gate индивидуально, не пакетно "добавили пять сразу,
проверили конец". Добавлять по одному, коммитить/тестировать по одному.

## Фаза 3 — Error Diffusion (отдельный, самостоятельно рискованный трек)

**Не начинать параллельно с Фазой 2.** ED — единственная часть, где
"правильная архитектура" не гарантирует успех за фиксированное время —
это исследовательская работа (parallel wavefront по антидиагоналям на
GPU-барьерах), не инженерная реализация известного паттерна.

**Подход:**
1. Прототип на синтетических данных (не в продукте) — доказать, что
   diagonal-parallel ED на GPU вообще даёт корректный результат и
   выигрыш, прежде чем интегрировать в граф.
2. Если прототип не подтверждается за разумное время — **осознанно
   оставить ED на CPU навсегда**, с явным checkpoint-механизмом в графе
   (GPU считает pattern-фильтры до ED, передаёт CPU, CPU передаёт
   обратно на GPU после) — это не откат к "неправильной архитектуре",
   это осознанная граница scope, которая должна быть в самом дизайне
   графа (Фаза 0.4) с самого начала, не постфактум.

**Не блокировать Фазы 1-2 ожиданием результата этого трека.**

---

## Фаза 4 — Display path (нативный surface / WebGPU)

**Отдельный трек, отдельный PoC, не блокирует Фазы 1-3.**

Простой readback-раз-на-кадр из Фазы 1 остаётся рабочим display-путём
сколь угодно долго — это не временная заглушка, которую обязательно
менять, а legitimate часть архитектуры до тех пор, пока zero-copy
display не даст измеримо другой класс результата (что при
GPU-resident graph из Фаз 1-2 уже не так критично, как было в v1 —
там проблема была N round-trip **на фильтр**, здесь остаётся 1
round-trip **на кадр**, что качественно другой порядок величины).

**Решение о Фазе 4 принимать после Фазы 2**, когда будет реальный
профиль: если 1 readback/кадр уже даёт приемлемый latency на целевых
документах — Фаза 4 становится "nice to have", не архитектурным долгом.

## Сводная последовательность

```
Фаза 0 (ADR, дни)         — контракты: формат тайла, layout, eviction tier, graph IR
Фаза 1 (недели)           — вертикальный срез: 1 документ, 1 фильтр, полный путь
   └─ gate: parity + benchmark + generation-safety, иначе назад в Фазу 0
Фаза 2 (недели-месяц)     — breadth: pattern-фильтры + palette, по одному
Фаза 3 (параллельно,      — ED прототип, самостоятельный риск, не блокирует 1-2
        отдельный трек)      если не получается — CPU checkpoint в графе, навсегда
Фаза 4 (после Фазы 2)     — display path PoC, решение по факту профиля
```

**Единственное, что можно смело выбросить прямо сейчас** — это весь
Path A (buffer pool поверх текущего per-tile v1). Он бессмысленен, если
цель — GPU-resident граф: работа над pooling/batching текущей per-tile
модели не переиспользуется в архитектуре Фазы 1, потому что модель
исполнения меняется полностью (не "тот же dispatch, но с пулом", а
"весь тайл никогда не покидает GPU между фильтрами"). Не тратить время
на v1-патчи, если решение — Path B.
