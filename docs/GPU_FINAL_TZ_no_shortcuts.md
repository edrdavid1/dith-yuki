# ТЗ: GPU-путь до индустриального стандарта (без костылей)

**Спека / задачи:** [`.cursor-spec/gpu-industrial-gate/`](../.cursor-spec/gpu-industrial-gate/SPEC.md)
([TASKS](../.cursor-spec/gpu-industrial-gate/TASKS.md)).

Только GPU. Ничего из остального продукта здесь не обсуждается.

**Контекст:** T0–T10 из `.cursor-spec/gpu-path-b/TASKS.md` формально
пройдены, итоговый отчёт называет статус `COMPLETE / GpuPreviewGate
READY`. **Это преждевременный вывод.** Архитектура построена правильно
(GPU-resident, compute graph, executor-поток, honest CpuCheckpoint для ED)
— сама конструкция не содержит костылей. Проблема не в архитектуре, а в
том, что **доказательства её пользы неполные**: цифры в отчёте не
покрывают то, что сама же спека (D6) требовала как обязательное условие
gate. "Готово" в смысле "код есть и работает" ≠ "готово" в смысле "можно
включать по умолчанию и не стыдно". Этот документ закрывает разрыв.

---

## Что уже сделано правильно (не трогать, не переделывать)

- GPU-resident tile cache, `Texture2DArray`, slot-based allocation —
  архитектурно корректно, соответствует industry baseline из спеки.
- `ComputeGraph` / `CpuCheckpoint` IR — правильная модель, ED честно
  вынесен как explicit checkpoint, не молчаливый fallback.
- Executor на отдельном потоке вместо `submit_lock` на всех воркерах —
  правильная модель (как в игровых движках/композиторах).
- `close_session` → GPU eviction, layer blend (T7.5), ED research-decision
  (permanent CPU checkpoint, задокументировано), display research-decision
  (no-go на нативный surface, 1 readback/frame) — все реализованы и
  задокументированы решениями, не забыты молча.
- 17 parity-тестов, eligibility unit-тесты, promote/demote round-trip тест
  — правильный набор корректности.

**Ничего из этого не переписывать.** Задача ниже — не "исправить архитектуру",
а "закрыть недостающие доказательства и две конкретные технические дыры".

## Блок 1 — Обязательно перед тем, как называть это "готово" (P0 для GPU)

### 1.1 Статистическая строгость бенчмарков

**Проблема:** отчёт приводит одно число p95 на сценарий (например,
"~10.6 vs ~11.0 ms"). Разница 4-6% неотличима от шума на одном прогоне.

**Что сделать:**
- Каждый benchmark-сценарий прогнать **минимум 20 раз** (release build),
  записать: median, p95, p99, стандартное отклонение.
- Формат отчёта на сценарий: `median: X ms (σ=Y), p95: Z ms, n=20 runs`.
- Если доверительные интервалы GPU и CPU пересекаются — считать результат
  "не доказано быстрее", не "примерно одинаково, но чуть лучше".

**Acceptance:** таблица с числом прогонов и σ для каждого сценария из
раздела 4 существующего отчёта, не только точечные оценки.

### 1.2 Сравнение с v1 per-tile GPU — обязательное условие D6, отсутствует в отчёте

**Проблема:** D6 явно требовал "faster than CPU worker pool **AND** faster
than v1 per-tile GPU". В отчёте есть только сравнение с CPU.

**Что сделать:**
- Прогнать `preview_latency_diag` со старым v1 путём (`DITHER_GPU=1`,
  legacy `dispatch_rgba32`) на тех же сценариях (Bayer viewport 40 L0,
  origin 100% и far-corner).
- Добавить третью колонку в таблицу бенчмарков: v1 per-tile GPU.

**Acceptance:** GPU-resident явно и статистически значимо (см. 1.1)
быстрее v1 на всех заявленных сценариях. Если где-то не быстрее — прямо
это зафиксировать, не замалчивать.

### 1.3 Cold-path бенчмарк (реалистичный сценарий, не steady-state)

**Проблема:** отчёт показывает cold promote (~43ms) отдельно от
steady-state (~10.6ms), но не как основной сценарий, хотя именно cold-path
— то, что пользователь видит большую часть времени (открытие документа,
переход в новую область при панорамировании, zoom).

**Что сделать:**
- Новый обязательный сценарий: полный cold cycle — открыть документ (или
  очистить GPU-кэш для этого документа), затем стандартный пользовательский
  жест (pan на 2-3 экрана, или zoom to fit) — замерить end-to-end latency
  до стабилизации превью, GPU-resident vs CPU, по методологии 1.1.
- Это отдельный, не опциональный gate-сценарий, наравне со steady-state.

**Acceptance:** число с той же строгостью (median/p95/σ, n=20), явно
подписанное "cold path", в основной таблице отчёта, не в сноске.

### 1.4 Реалистичный пользовательский стек с ED-checkpoint

**Проблема:** "~4× tax" от чистого Bayer-baseline — относительное число
без абсолютного контекста. Неизвестно, быстрее ли GPU-путь **со
checkpoint** чем чистый CPU-путь на том же стеке — это единственное
число, которое реально решает, стоит ли включать GPU по умолчанию для
типичного пользователя (у которого почти наверняка есть ED в стеке).

**Что сделать:**
- Взять 2-3 репрезентативных пресета из реального использования (не
  синтетика): например `Adjust → FS → Bayer`, `Palette Strict → FS`,
  `CRT → Halftone` (без ED, для контраста).
- На каждом — полное сравнение GPU-resident (с checkpoint, где применимо)
  vs чистый CPU, по методологии 1.1, на реалистичном документе (тот же
  портрет/тестовое изображение, что использовалось в Track Q QA).

**Acceptance:** таблица "пресет × путь × latency" — явно видно, для каких
реальных пользовательских стеков GPU-resident выигрывает, а для каких
проигрывает CPU из-за overhead checkpoint. Это не блокер архитектуры — это
информация, необходимая для решения в Блоке 3 (что показывать в UI по
умолчанию).

### 1.5 Generation-safety тест — явное подтверждение

**Проблема:** T6 acceptance требовал тест класса TICKET-1 (GPU slot,
вытесненный под pressure, повторно запрошенный — не должен вернуть stale
generation). В разделе 7 отчёта не назван явно среди перечисленных тестов.

**Что сделать:**
- Найти этот тест в кодовой базе. Если существует — назвать явно в
  итоговом отчёте (имя теста, файл).
- Если не существует — написать: promote тайл на GPU → инициировать
  eviction под pressure (другой документ, active/inactive) → тайл
  вытеснен → повторный запрос того же `TileKey` с новым `document_gen` →
  убедиться, что возвращается свежий пересчёт, не stale-данные из
  случайно не до конца освобождённого слота.

**Acceptance:** тест существует, зелёный, явно упомянут в финальном
отчёте по имени — не подразумевается внутри "17 resident_parity green".

## Блок 2 — Две конкретные технические дыры (найдены в ревью спеки, статус после реализации неизвестен)

### 2.1 VRAM ping-pong — подтвердить реальное потребление

**Проблема (из ревью SPEC.md, D1):** формулировка "dual array
(`array_a`, `array_b`)" может означать, что реальное VRAM-потребление
вдвое больше заявленного `vram_budget_bytes` (256 MiB бюджет → фактически
512 MiB, если оба массива полного размера `max_slots`).

**Что сделать:**
- Проверить фактическую реализацию: `array_b` — это полный дубликат
  `max_slots` слотов, или маленький scratch-буфер только на размер одного
  frame batch (сколько тайлов обрабатывается в текущем кадре)?
- Если полный дубликат — задокументировать явно: "фактический VRAM
  budget = 2 × заявленного" — и решить, снижать ли заявленный бюджет
  вдвое, или переделать на маленький scratch-буфер (рекомендованный в
  ревью вариант — дешевле, ping-pong нужен только между соседними
  compute-passes одного тайла, не между разными тайлами кэша).
- Замерить фактическое VRAM-потребление процесса (Instruments/Activity
  Monitor на macOS) при заполненном кэше, сравнить с заявленным числом.

**Acceptance:** явное число в документации ("реальный VRAM budget = X
MiB при заявленных Y MiB") + либо принятое как есть с обновлённой
документацией, либо исправлено на scratch-буфер с новым замером.

### 2.2 `pixel_size > 1` — явное решение по scope

**Проблема (из ревью SPEC.md):** не упомянут ни в Non-goals (как ED), ни
в планах (как Halftone/CRT в T7). Молчание — не то же самое, что решение.

**Что сделать:** явно выбрать один из двух вариантов и записать в
документацию (`docs/gpu-path-b-adr.md` или итоговый отчёт):

- **(a) Non-goal, аналогично ED.** `pixel_size > 1` использует
  `BlockRepresentativeCache` — принципиально другой паттерн вычисления
  (representative-пиксель на блок), не per-pixel shader. Если решено не
  делать — добавить как `CpuCheckpoint(PixelSizeBlock)` или полный
  CPU-fallback для этого случая, задокументировать наравне с ED-решением.
- **(b) Запланировать в Phase 2/3** — потребует отдельного ADR-подпункта
  (аналогично D3 для ED) под block-granularity compute, не втискивать
  "заодно" в существующий T7 список без дизайна.

**Acceptance:** явная строка в документации, один из двух вариантов
выбран и обоснован, не остаётся неявным пробелом.

## Блок 3 — Решение о production rollout (только после Блоков 1 и 2 закрыты)

**Не начинать этот блок, пока 1.1–1.5 и 2.1–2.2 не закрыты.** Иначе
решение о дефолтном включении GPU принимается на неполных данных — ровно
та ошибка, которую отчёт уже совершил один раз.

### 3.1 Честное решение по дефолту

На основе цифр из 1.4 (реалистичные пресеты) — решить:

- Если GPU-resident выигрывает на **большинстве** реалистичных
  пользовательских стеков (включая типичные с ED-checkpoint) — можно
  рассматривать `DITHER_GPU_PREVIEW` on by default для eligible
  документов/фильтров.
- Если выигрывает только на узком подмножестве (например, только
  Bayer-only без ED, без палитры) — оставить opt-in, но **честно** описать
  в UI/документации границы: "GPU ускоряет паттерн-дизеринг без ED и
  палитры; для полного стека с ED разницы нет или CPU быстрее".
- **Не включать по умолчанию "потому что технически работает"** — только
  на основе цифр из 1.4.

### 3.2 Что можно удалять только после 3.1

- v1 `dispatch_rgba32` / `gpu_bridge` try_* пути — удалять только после
  soak-периода на реальных пользователях с `DITHER_GPU_PREVIEW=1`, не
  сразу после прохождения Блоков 1-2.
- `DITHER_GPU` legacy semantics — то же самое, после soak.

### 3.3 UI-тоггл — только с честной формулировкой

Если/когда добавляется UI-переключатель "GPU acceleration" — текст рядом
с ним должен отражать реальные границы (см. 3.1), не общую формулировку
"ускорить рендеринг". Пример honest copy: "Ускоряет паттерн-дизеринг
(Bayer, Halftone, CRT) и работу с палитрами. Error diffusion всегда
считается на CPU." — не "Enable GPU acceleration" без пояснений.

## Что считается "костылём" здесь и не должно появиться при доработке

Явный список — чтобы агент не воспроизвёл на новом витке те же паттерны,
что уже были в v1:

- Возврат к `submit_lock`, покрывающему весь round-trip (включая
  readback ожидание) — синхронизация должна оставаться на уровне
  `queue.submit()` только, не шире.
- Молчаливый fallback на CPU без счётчика/лога при GPU-ошибке — как и в
  v1, любой fallback должен быть наблюдаемым (счётчик, warn), не тихим.
- Объявление "GPU acceleration" в маркетинге/UI до прохождения Блока 1
  целиком — это ровно та ошибка, которой посвящён этот документ.
- Добавление `pixel_size > 1` "заодно" при работе над чем-то другим без
  отдельного дизайн-решения (см. 2.2) — тот же паттерн, что привёл к
  пропущенным Non-goals в исходной спеке.
- Расширение eligibility (новые фильтры на GPU) без индивидуального
  parity + perf gate на каждый — правило T7 ("по одному, не пакетно")
  должно сохраняться и после этого ТЗ, не только в исходной фазе.

**Итоговый критерий "готово к индустриальному стандарту":** не "T0-T10
закрыты", а "решение о дефолтном включении GPU принято на основе полных,
статистически строгих данных, охватывающих реалистичные пользовательские
сценарии, включая худший случай (ED-checkpoint tax) и худшую фазу
(cold path)". Пока это не так — текущий статус честно называется
"архитектура построена правильно, экономическое обоснование неполное",
не "COMPLETE / READY".
