## 1. Риск: Serpentine Scanning × Cross-Tile Wavefront (Track A1)

Track A1 уже проектирует полноценную кросс-тайловую диффузию через
диагональный wavefront-обход (тайл `(X,Y)` ждёт данные от `(X-1,Y)`,
`(X,Y-1)`, `(X-1,Y-1)`, `(X+1,Y-1)`) — это построено на **фиксированном**
направлении обхода (слева направо, сверху вниз).

Serpentine scanning переключает направление на нечётных строках (справа
налево) **внутри тайла**. Если это сделать не подумав, у cross-tile
wavefront два способа сломаться:

1. Если serpentine работает только внутри одного тайла, а направление
   между тайлами остаётся фиксированным L→R — на границе тайла, где
   внутренняя строка идёт R→L, а следующий тайл всё равно ждут прихода
   данных "слева", возникает несостыковка направления передачи ошибки
   ровно на стыке — то есть Serpentine, реализованный наивно, **заново
   вносит те самые швы**, которые Track A1 закрывает.
2. Serpentine определяется на уровне строки (`y % 2`), а `y` здесь должен
   быть **глобальным**, не локальным — иначе четность строки будет
   расходиться между тайлами по той же причине, по которой раньше ловили
   баг с halo/`pixel_size` (несовпадение локальной и глобальной системы
   отсчёта на границе).

**Что делать:** реализовывать Serpentine **после** того как Track A1 закрыт
и его тесты зелёные (не параллельно — Serpentine меняет предположения, на
которых A1 строит `IncomingErrorBuffer`). При реализации:
- Чётность строки — от `GlobalCoord.y`, не от локальной координаты тайла.
- Направление обхода на тайле `(X, Y)` должно быть согласовано с тем, какие
  соседи ему шлют вклад: если строка глобально R→L, входящий вклад "справа"
  должен по-прежнему логически означать "от тайла, который был обработан
  раньше по wavefront-порядку", а не буквально "физически справа на экране".
  Проще всего: параметризовать `IncomingErrorBuffer`-модель направлением
  строки как входным аргументом на уровне тайла, вычисляемым из
  `GlobalCoord`, а не переписывать саму wavefront-архитектуру.
- Обязательный тест: серпантин-режим на 2×2 тайлах, шов на границе
  отсутствует **и** на чётных, и на нечётных глобальных строках.

## 2. Риск: Angle/Rotation Bayer × BlockRepresentativeCache (Track A2)

Track A2 строит `BlockRepresentativeCache`, ключ которого — `(block_x,
block_y) = (aligned_x / pixel_size, aligned_y / pixel_size)` в
axis-aligned глобальной сетке. Angle/Rotation для Bayer (не CMYK Halftone,
где угол сейчас фиксирован per-channel и не завязан на `pixel_size`-блоки)
вводит **повёрнутую** систему координат для сэмплирования паттерна.

Это две разные оси, которые легко перепутать при реализации:
- `pixel_size` — размер супер-пикселя (сколько экранных пикселей красятся
  одним цветом-представителем). Это блочная агрегация, ключ в
  `BlockRepresentativeCache`.
- `Angle` — поворот **паттерна** (сетки Bayer/растра), под которым берётся
  порог для каждого (уже возможно блочно-агрегированного) пикселя. Это
  преобразование координаты **перед** `pattern_cell()`, не имеет отношения
  к блочному кэшу представителей.

**Что делать:** явно зафиксировать в реализации, что `Angle` применяется
**после** получения представителя блока из `BlockRepresentativeCache` (или
после `GlobalCoord::aligned(pixel_size)`, если `pixel_size=1` и кэш не
задействован) — то есть порядок операций:

```text
global coord → aligned(pixel_size) → [BlockRepresentativeCache lookup] → rotate(angle) → pattern_cell(matrix_size) → threshold compare
```

Не наоборот (не поворачивать координату до блочной агрегации) — иначе
блоки перестанут быть осе-выровненными прямоугольниками, и вся модель
`BlockRepresentativeCache` (которая ключуется по axis-aligned `block_x/
block_y`) перестанет быть корректной, придётся её полностью переделывать
под произвольный угол. Поворачивать только сам паттерн сэмплирования, не
геометрию блоков.

**Тест:** `pixel_size > 1` и `Angle != 0` одновременно — швов на границе
тайла нет, блоки остаются видимыми как прямоугольники (не искажаются
поворотом), паттерн внутри повёрнут.

## 3. Риск: Per-filter Opacity/Blend Mode × Error Diffusion residuals

Это самое архитектурно значимое изменение в исходном плане — оно меняет
модель применения фильтра с "чистая трансформация" на "трансформация +
блендинг с собственным входом".

**Опасность:** `ErrorResidualsStore`/`IncomingErrorBuffer` (Track A1)
считают и передают остаток ошибки, основываясь на **полной** диффузии
(100% amount). Если результат фильтра потом блендится с pre-filter тайлом
на, скажем, 50% opacity — какое значение должно распространяться соседу:
то, что реально видно на экране (блендированное), или полная диффузия,
как будто opacity=100%?

**Решение — распространять по полной диффузии, блендить только видимый
результат:**
- `ErrorResidualsStore` заполняется на основе **полного** диффузного
  прохода (opacity никак не участвует в математике распространения
  ошибки) — это гарантирует, что математика диффузии остаётся корректной
  и предсказуемой независимо от того, какой opacity потом выставит
  пользователь.
- Opacity/Blend Mode применяется **в конце**, как последний шаг перед
  записью в `Processed`-кэш: `output = blend(pre_filter_tile,
  full_diffusion_result, opacity, blend_mode)`. Это чисто визуальный
  пост-шаг, не влияет на то, что "утекает" соседям.

**Архитектурно:** реализовать как **обёртку на уровне диспетчера
применения фильтра** (`tile_pipeline.rs`/`compute_processed_tile`), не
как параметр внутри каждого отдельного фильтра — иначе логику
"сохрани pre_filter копию → примени фильтр → блендни" придётся
дублировать в каждом из ~15 фильтров, с гарантированным расхождением
поведения между ними со временем.

```rust
fn apply_filter_with_blend(pre: &PixelTile, instance: &FilterInstance, ctx: &FilterCtx) -> PixelTile {
    let full_result = apply_filter(pre, instance, ctx); // существующий путь, без изменений
    if instance.opacity >= 1.0 && instance.blend_mode == BlendMode::Normal {
        return full_result; // fast path, самый частый случай — не тратить лишний blend-проход
    }
    blend(pre, &full_result, instance.opacity, instance.blend_mode)
}
```

**Тест:** ED-фильтр с `opacity=50%` в стеке на 2×2 тайлах — швов нет (потому
что распространение ошибки использует `full_result`, не блендированный),
визуальный результат — корректный 50%-blend с исходником.

**Порядок:** делать Track I **после** Track A1 закрыт — иначе придётся
переделывать место, куда встраивается blend-обёртка, если модель residuals
поменяется.

## 4. Треки без архитектурных рисков — можно почти сразу и параллельно

- **Track M** (доп. ED-ядра JJN/Stucki/Burkes/Sierra): чисто добавление
  весовых матриц в существующий diffusion-фреймворк (после того как Track
  A1 закрыт, поскольку они используют тот же `IncomingErrorBuffer`).
  Serpentine из Track M — после A1, отдельно от ядер (ядра сами по себе не
  конфликтуют с wavefront, только Serpentine).
- **Track H** (Threshold Bias/Offset): тривиальный параметр порога, без
  зависимостей, можно сразу. Angle/Rotation — см. §2, после A2.
- **Track J** (Glitch: RGB Shift, Block Displace): новые фильтры,
  независимы от диффузии/halftone. **Важно:** Block Displace читает пиксели
  со смещением — использовать `GlobalCoord`, не ручную арифметику (тот же
  урок, что уже стоил времени в Track A/C). PRNG на seed — детерминированный
  XorShift64, seed должен быть частью `FilterParams` (персистится, чтобы
  результат был воспроизводим при пересчёте тайла).
- **Track K** (Unified Slider/NumberInput): чистый frontend, никаких
  зависимостей от backend-треков. **Делать рано** — все новые фильтры
  (Halftone UI, Wave UI, CRT UI, Glitch UI, ED-kernel selector) будут
  писать параметры через этот компонент; если он появится после того как
  5 панелей параметров уже написаны на голых HTML input — придётся
  переписывать 5 панелей. Debounce 100ms — на уровне самого компонента,
  не дублировать в каждой панели.
- **Color Lab extraction weighting** (Chroma/Contrast): расширение уже
  существующего `generate.rs`, независимо, любое время.

## Критерии приёмки мастер-плана

1. Ни один из пунктов §1–§3 не реализован до того, как соответствующий
   блокирующий трек (A1 или A2) закрыт и его тесты зелёные.
2. Serpentine и Angle/Rotation имеют собственные seam-тесты, отдельные от
   базовых тестов A1/A2 (они проверяют новую степень свободы, не
   переиспользуют старые тесты как достаточное покрытие).
3. Per-filter Opacity/Blend реализован как единая обёртка в диспетчере,
   не продублирован по фильтрам — проверяется code review, не только
   тестами.
4. Track K существует до того, как пишется UI для Track M/H/J новых
   параметров (проверяется по факту: если новая панель параметров написана
   на сырых `<input>` вместо `Slider`/`NumberInput` — это регрессия
   процесса, не только кода).
