## 0. Что уже есть и на что опираться (не изобретать заново)

- **Прецедент "recipe без данных, новая сущность при импорте"**: Color Lab
  Apply/Import/Extract уже всегда создаёт **новую** палитру в документе, не
  ре-использует существующий id (`COLOR_AND_COLOR_LAB.md`, известный gap,
  но здесь это фича, не баг — прямо то поведение, которое нужно для sharing).
  `.dyuki` должен следовать этому же паттерну: импорт всегда создаёт новые
  сущности (палитру, фильтры) с новыми id в целевом документе, никогда не
  пытается сматчить/переиспользовать существующие id.
- **Прецедент миграции схемы**: `(DitherMode, color_depth)` → `DitherParamsV2`
  через `From` impl — используем тот же идиом для версионирования форматов
  файлов (`format_version` + цепочка migration-функций), не изобретаем новую
  систему версионирования.
- **Sandbox path validation** (`engine_io::sandbox::resolve_user_path`) —
  для user-предоставленных путей (Open/Save диалоги). Для **внутренне
  генерируемых** путей (распакованные ассеты проекта во временную/app-data
  директорию) эта проверка не нужна и не должна применяться — это разные
  классы путей, не путать в реализации.
- **Threshold map кэш** (`ThresholdMapCache`, keyed by `(path, mtime)`) —
  при работе с embedded/распакованными threshold map PNG нужен стабильный
  синтетический путь (content-addressed в app-data
  `asset-cache/threshold-maps/{content_hash}.png`, без project/import uuid),
  чтобы кэш продолжал
  работать без изменений в его API.

## 1. Общая архитектура контейнера

**Оба формата — zip-архивы** с общей внутренней "asset embedding" подсистемой
(один переиспользуемый модуль в `engine-project` или новом `engine-serialize`,
решить при спеке — не дублировать код embedding между `.dyproj` и `.dyuki`).

Почему zip, а не единый бинарник или чистый JSON с base64:
- Zip даёt бесплатное сжатие для растровых слоёв (существенно для `.dyproj`,
  который хранит полноразмерные изображения).
- Инструментарий уже привычен индустрии для похожих контейнеров (`.ai`,
  `.kra`, `.ora`, `.docx` — все zip с манифестом внутри).
- При отладке можно открыть `unzip`/архиватором и посмотреть содержимое —
  дешёвая observability на этапе разработки.
- `.dyuki` обычно маленький (нет растровых слоёв), но использование того же
  контейнера даёт единую кодовую базу embedding для threshold maps/палитр
  вместо двух разных схем.

Rust: `zip` crate (добавить в workspace).

## 2. `.dyproj` — формат проекта

### 2.1 Что персистится vs что рантайм-only (критично)

| Поле | Персистить? | Причина |
|---|---|---|
| `Document.width/height/color_profile` | ✅ | Данные документа |
| `Document.root` (layer tree) | ✅ | Структура/настройки |
| `Document.palettes` | ✅ | Данные документа |
| `Document.revision` | ❌ | Рантайм-счётчик кэша, сбросить в 1 при загрузке |
| `Document.generations` | ❌ | `GenerationTracker`, пересоздать пустым |
| `Layer.filters[].requires_full_row` | ❌ | Пересчитывается из `kind` при загрузке (как для legacy Dither-миграции) |
| `FilterInstance.id` (UUID) | ⚠️ решение ниже | См. §2.4 про ID |
| Растровые данные слоя (raw pixels) | ✅, как PNG | Иначе документ нельзя восстановить |
| Panel layout / viewport / window state | ❌ | Это app-level UI state (уже отдельно персистится через `panel_persistence.rs`), не часть документа — не дублировать |

### 2.2 Структура архива

```
project.dyproj (zip)
├── manifest.json          # format_version, app_version, created_at, modified_at, doc dims
├── document.json          # Document minus raw pixels minus рантайм-поля (см. §2.1)
├── layers/
│   ├── {layer_id}.png     # Raw source изображение слоя (lossless PNG, даже если
│   │                       # исходный импорт был JPEG — избегаем повторного
│   │                       # сжатия на каждом save/reopen цикле)
│   └── {layer_id}.mask.png  # Опционально, если layer.mask задан
└── assets/
    └── threshold_maps/
        └── {content_hash}.png  # Embedded копии custom PNG threshold maps,
                                  # на которые ссылаются DitherV2 CustomPng-фильтры
                                  # в этом документе
```

Adjustment-слои (`LayerKind::Adjustment`) не имеют `layers/{id}.png` — у них
нет растровых данных по определению модели.

### 2.3 `document.json` — форма

Прямое отражение `Document`/`LayerNode`/`Layer`/`LayerGroup`/`FilterInstance`/
`FilterParams`/`Palette` из `engine-project`, **минус** поля из таблицы §2.1,
**плюс**:
- `layer.raw_asset: Option<String>` — имя файла в `layers/` (вместо реальных
  пиксельных данных).
- Ссылки на threshold map внутри `DitherParamsV2` (сейчас, вероятно, это путь
  на диске пользователя) — при сохранении заменяются на `{content_hash}.png`
  внутри `assets/threshold_maps/`, оригинальный путь пользователя **не**
  сохраняется (он может не существовать на машине, где документ откроют).

### 2.4 ID: пересобирать заново при загрузке, не пытаться сохранить исходные

**Решение:** `LayerId`, `PaletteId`, `FilterInstanceId` при `open_project`
**генерируются заново** (не восстанавливаются из файла как есть), с построением
remap-таблицы (старый id из файла → новый рантайм-id) для разрешения
внутренних ссылок (`palette_id` в фильтрах, ссылки маски на другой layer id,
если такие есть в модели — проверить `MaskRef` при спеке, возможно она
всегда inline-изображение, а не ссылка на layer, тогда remap для неё не
нужен).

**Почему не сохранять id как есть:** это избавляет от необходимости
персистить/восстанавливать внутренние счётчики генерации id, и не создаёт
риска коллизий id между открытым документом и вновь загруженным (актуально
уже сейчас даже при single-document ограничении — при закрытии и повторном
открытии другого файла счётчики должны быть согласованы). Ничего в текущем
UI не показывает пользователю сырые id напрямую (судя по DTO — только имена/
структура), так что это не наблюдаемое пользователем изменение поведения.

### 2.5 Открытие проекта — переиспользовать существующий путь замены документа

`open_project(path)` должен зайти в тот же механизм, что сейчас использует
`load_image` для замены `AppState.document_handle` (документ единственный,
`doc_id=1`, как и сейчас — **не** реализовывать multi-document в рамках этой
задачи, это отдельный будущий пункт из TODO). Отличие от `load_image` только
в источнике данных: не "decode одно изображение → decompose", а "распаковать
zip → для каждого layer.raw_asset decode PNG → decompose в тайлы конкретного
слоя, для каждого повторить".

**Важно:** после распаковки threshold map PNG во временную/app-data
директорию — зарегистрировать в `ThresholdMapCache` под синтетическим путём
(§0), не пытаться валидировать этот путь через `resolve_user_path` (это
внутренне сгенерированный путь, не пользовательский ввод).

### 2.6 Версионирование

`manifest.json.format_version: u32`, старт с `1`. При открытии файла с
`format_version` меньше текущего — прогнать цепочку migration-функций
(`migrate_v1_to_v2(document_json) -> document_json`, и т.д.), тем же идиомом,
что уже применяется для `DitherMode` → `DitherParamsV2`. При
`format_version` больше текущего (файл из более новой версии приложения) —
явная ошибка "обновите приложение", не пытаться грузить частично.

### 2.7 IPC-команды (добавить в `commands.rs`, рядом с существующими)

| Команда | Аналог существующей | Отличие |
|---|---|---|
| `save_project(path)` | — | Сериализует текущий `Document` + собирает zip |
| `open_project(path)` | `load_image` | Заменяет документ, источник — zip, не сырое изображение |
| `save_project_as(path)` | — | То же что save, другой путь, обновляет "текущий путь проекта" в состоянии |

Путь текущего открытого/сохранённого проекта нужно где-то держать в
`AppState` (для "Save" без диалога после первого "Save As") — решить при
спеке, куда именно (вероятно рядом с `document_handle`).

## 3. `.dyuki` — sharable pattern (recipe)

### 3.1 Что это, если конкретно

Не документ, не изображение — **упорядоченный список `FilterInstance`**
(тот самый `layer.filters: Vec<FilterInstance>`, который применяется к
одному слою) плюс всё, что нужно, чтобы эти фильтры воспроизводимо
работали на чужой машине:
- Embedded палитры, на которые ссылаются `palette_id` внутри фильтров.
- Embedded threshold map PNG, на которые ссылаются `DitherV2::CustomPng`.

**Не входит:** сам растровый слой, layer offset/blend_mode/opacity/mask
(это свойства конкретного слоя в конкретном документе, не часть "рецепта
обработки" — паттерн применяется к любому целевому слою, его собственные
layer-level свойства не трогаются).

### 3.2 Структура архива

```
pattern.dyuki (zip)
├── manifest.json     # format_version, app_version_min, name, description,
│                       author (опционально), created_at
├── filters.json       # Vec<FilterInstance>, минус id (пересоздаются),
│                       # минус requires_full_row (пересчитывается),
│                       # palette_id внутри params заменён на локальный
│                       # placeholder-ключ (см. ниже), не на реальный id
├── palettes.json       # { "placeholder-key": Palette-данные (name, colors) }
│                        # embedded по значению, не по ссылке
└── assets/
    └── threshold_maps/
        └── {content_hash}.png
```

### 3.3 Импорт — маппинг placeholder → новый id

`import_pattern(path, target_layer_id)`:
1. Распаковать zip, провалидировать `manifest.format_version` (§2.6, тот же
   идиом миграций, общий с `.dyproj`).
2. Для каждой записи в `palettes.json` — вызвать существующий путь создания
   палитры (тот же код, что стоит за `add_palette`/Color Lab Apply) →
   получить новый `PaletteId`. Построить map `placeholder-key → новый id`.
3. Распаковать threshold map PNG в app-data (§0), зарегистрировать в кэше.
4. Для каждого `FilterInstance` из `filters.json`: сгенерировать новый
   `FilterInstanceId`, подставить новые `palette_id` из map шага 2, новые
   threshold-map-пути из шага 3, пересчитать `requires_full_row` из `kind`.
5. Добавить получившиеся `FilterInstance` в `target_layer_id.filters`
   (append в конец существующего стека, не заменять существующие фильтры
   слоя — импорт паттерна дополняет, не перезаписывает; если нужен режим
   "заменить весь стек", это отдельная явная опция UI, не поведение по
   умолчанию).
6. Инвалидировать/пересчитать тайлы целевого слоя как при обычном
   `add_filter`.

### 3.4 Экспорт

`export_pattern(layer_id, filter_instance_ids: Option<Vec<Id>>, path)`:
- Если `filter_instance_ids` не задан — экспортировать весь `filters` стек
  слоя.
- Если задан — экспортировать только выбранное подмножество (в UI это может
  быть "выделить несколько фильтров в EffectSettingsPanel → Export as
  pattern").
- Собрать уникальные `palette_id`/threshold-map-пути, встречающиеся среди
  экспортируемых фильтров, embedding их в архив как в §3.2.

### 3.5 Совместимость версий приложения

`manifest.app_version_min` — минимальная версия приложения, способная
прочитать этот файл (не путать с `format_version`, который про схему
данных). Нужно на случай если `.dyuki` ссылается на `DitherModeV2` variant,
добавленный позже релиза, которым паттерн открывают (например, кто-то на
свежей версии экспортировал паттерн с CMYK Halftone, поделился с человеком
на старой версии без этого фильтра). При несовпадении — явная ошибка с
понятным сообщением, не молчаливый silent-drop фильтра из стека.

## 4. Общие открытые вопросы — оставлены на решение агента при спеке

Не решать заранее без причины, но не игнорировать при написании спеки:

1. **Расширение файлов / регистрация в OS** (двойной клик открывает
   приложение) — `tauri.conf.json` file associations + иконки. Низкий
   приоритет для MVP фичи, но упомянуть как отдельную задачу в tasks.md,
   не блокирует ядро функциональности.
2. **UI для Export/Import pattern** — где именно в интерфейсе (контекстное
   меню на фильтре в `EffectSettingsPanel`? Отдельная кнопка?) — решить при
   дизайне UI, не архитектурный вопрос.
3. **Autosave/crash recovery для `.dyproj`** — явно вне скоупа этой фичи,
   пометить как future improvement, не блокирует MVP.
4. **Лимит размера `.dyproj`** — при документах с большим числом крупных
   растровых слоёв архив может быть тяжёлым; решить, нужен ли warning/лимит,
   по аналогии с существующим `Max 8192×8192` ограничением на изображения.
5. **MaskRef modeling** — ✅ зафиксировано в track-e design: `MaskStorage::External(LayerId)`
   → remap LayerId; отдельный `{layer_id}.mask.png` в v1 **не** используется
   (`EmbeddedVector` — placeholder, без raster-файла).

## 5. Критерии приёмки (для итоговой спеки/тасков)

1. `.dyproj`: save → close app / reopen app → open_project → документ
   визуально идентичен (тот же layer tree, те же фильтры с теми же
   параметрами, та же палитра, тот же композит на выходе — сравнить PNG
   экспорт до/после round-trip).
2. `.dyproj`: округление версии — файл с `format_version` из будущего даёт
   понятную ошибку, не крашится и не открывается частично.
3. `.dyuki`: экспорт стека фильтров с палитрой и custom threshold map →
   импорт в **другой, пустой** документ на чистой машине (без исходных
   файлов палитры/threshold map на диске) → результат обработки визуально
   идентичен исходному (доказывает, что embedding работает, ничего не
   зависит от путей на диске экспортёра).
4. Повторный импорт того же `.dyuki` дважды в один слой → два независимых
   набора фильтров с разными id, каждый рабочий (не коллизия/перезапись).
5. `requires_full_row` и прочие рантайм-поля после open/import совпадают с
   тем, что дал бы обычный `add_filter` с теми же параметрами (не расходятся
   от того, что было в файле).
