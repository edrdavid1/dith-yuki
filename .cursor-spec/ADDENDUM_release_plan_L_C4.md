Спеки: [RELEASE_TRACKS.md](./RELEASE_TRACKS.md). Track L →

## Решение по идентичности продукта

Оба направления (глубокий perceptual-инструмент и универсальный
ретро-редактор) — равнозначны для релиза. Это влияет на **распределение
ресурсов** (не откладывать Glitch/CRT/ED-ядра ради Color Lab и наоборот,
вести параллельно), но **не отменяет** технические зависимости из
`ROADMAP_production_release.md` — Serpentine всё ещё должен идти после A1,
Angle всё ещё после A2, Opacity/Blend всё ещё после A1, независимо от того,
что "одинаково важно". Важность — про то, куда распределять людей между
независимыми треками; порядок внутри треков с реальными архитектурными
рисками остаётся как есть.

Добавлены два трека, оба независимые технически — их можно вести
параллельно чему угодно, включая друг друга.

## Track L — 3D Oklab-визуализатор палитры

Спека: [track-l-oklab-volume/](./track-l-oklab-volume/).

### Backend

Не дублировать sRGB→Oklab конверсию на фронте (JS-реализация неизбежно
разойдётся с Rust-версией в `oklab.rs` рано или поздно, разные округления
на float — тот же класс проблемы, что уже обсуждался с parity-тестами в
Track D). Один источник истины — Rust.

Новая IPC-команда в `commands.rs`:

```rust
#[tauri::command]
fn get_palette_oklab(palette_id: PaletteId) -> Result<Vec<OklabPointDto>, AppError> {
    let palette = document.get_palette(palette_id)?;
    Ok(palette.colors.iter().map(|c| {
        let oklab = Oklab::from(*c); // переиспользовать существующую oklab.rs
        OklabPointDto { l: oklab.l, a: oklab.a, b: oklab.b, srgb_hex: to_hex(*c) }
    }).collect())
}
```

Дополнительно: статический меш границы sRGB-гамута в Oklab-координатах
(для референсной wireframe-сферы/оболочки на фоне облака точек палитры —
то, что в исходном видении Color Lab называлось "показывать дыры в
палитре"). Это можно посчитать **один раз** оффлайн (не на каждый рендер) —
сгенерировать координаты границы гамута скриптом при разработке, сохранить
как статический asset (JSON/бинарник с вершинами), не пересчитывать в
рантайме на каждое открытие панели.

### Frontend

Новый компонент в Color Lab, например `PaletteVolumeViewer.tsx` (Three.js,
уже в списке разрешённых библиотек для этого окружения):
- Point cloud: каждая точка — цвет палитры в координатах `(a, L, b)` (или
  выбрать удобную ось-маппинг для интуитивного просмотра — L обычно логично
  ставить вертикальной осью).
- Referentce mesh — полупрозрачная граница sRGB-гамута (из статического
  asset выше).
- Orbit controls (вращение/зум мышью).
- Клик по точке → подсвечивает соответствующий цвет в списке `manual edit`
  (курсор/выделение синхронизируются, не два независимых состояния).

**Non-goals для MVP этого трека:** "изолировать пиксели на холсте,
квантованные в этот цвет" (было в исходном видении Color Lab) — это требует
отдельного прохода по тайлам композита и подсветки, содержательно другая
фича, делать отдельным треком после того как базовый визуализатор
стабилен, не смешивать в один PR.

### Тесты
- `get_palette_oklab` на известной палитре (например Game Boy 4 цвета из
  built-in presets) даёт ожидаемые Oklab-координаты (сверить с ручным
  расчётом/референсным значением).
- Визуальный тест (ручной): открыть палитру с явно "дырявыми" участками
  (например, только тёмные и только светлые цвета, без среднего диапазона)
  → в 3D-облаке видна пустота в середине.

## Track C4 (формализовано) — SVG Export

> As-built C4 v1 уже в дереве (`engine-io::svg_export`, 2026-08-12).
> Спека дожима: [track-c4-svg-followup/](./track-c4-svg-followup/) (C4.1).
> Ниже — исходный текст аддендума; IPC `export_svg` **не** заводить — расширять
> существующий `export_image`.

Ранее упоминался как независимый пункт, здесь — детализация.

### Backend

`crates/engine-io/src/svg_export.rs` (или `engine-project/src/export/svg.rs`
— выбрать по факту, куда сейчас смотрит остальной export-код, не заводить
новое место без причины).

Два режима, как в исходном плане:

**1. Greedy Meshing** (для пиксельных сеток, обычный дизеринг/палитровый вывод):
- Пройти по финальному композиту документа (уже отрендеренный результат,
  тот же путь данных, что использует растровый export).
- Построчно объединять соседние пиксели одного цвета в максимальные
  прямоугольники (стандартный greedy meshing алгоритм — сначала по строке,
  потом попытка расширить прямоугольник вниз пока все строки совпадают).
- Генерировать `<rect x y width height fill="#HEX"/>` на каждый
  прямоугольник.

**2. Contour Tracing** (для органичных форм/печатных векторов):
- Квантизация/бинаризация композита.
- Connected component labeling → внешние/внутренние контуры.
- Генерировать `<path d="M... Z" fill="..."/>`.

**Выбор режима** — параметр экспорта, не автоопределение (пользователь
явно выбирает Greedy Meshing для пиксель-арта или Contour Tracing для
печатных/органичных форм — попытка угадать автоматически даст
непредсказуемый результат и по сложности не проще явного выбора).

### IPC

```rust
#[tauri::command]
fn export_svg(path: String, mode: SvgExportMode) -> Result<(), AppError>;

enum SvgExportMode { GreedyMesh, ContourTrace { threshold: f32 } }
```

### Frontend

Пункт в Export-меню рядом с существующим PNG/растровым экспортом, с
выбором режима (radio: Pixel Grid / Contour) — переиспользовать тот же
save-dialog механизм, что уже есть для растрового экспорта, не писать
новый диалог с нуля.

### Тесты
- Greedy Meshing на простом тестовом изображении (несколько явных
  прямоугольных областей одного цвета) → количество `<rect>` в выводе
  соответствует ожидаемому минимуму (не по одному `<rect>` на пиксель —
  это будет означать, что мерджинг не сработал).
- Contour Tracing на изображении с известной топологией (круг с дыркой)
  → путь содержит и внешний, и внутренний контур.
- Экспортированный SVG открывается валидным SVG-парсером (не просто
  "файл записался", а действительно валидный XML/SVG).

## Обновлённая сводная последовательность

```text
Параллельно, без ограничений по порядку между собой:
  Track K (UI Slider unification)
  Track J (Glitch)
  Track H § Threshold Bias (не Angle — тот после A2)
  Color Lab extraction weighting
  Track L (3D Oklab visualizer)     ← [track-l-oklab-volume/](./track-l-oklab-volume/)
  Track C4.1 (SVG follow-up)         ← [track-c4-svg-followup/](./track-c4-svg-followup/)

После A1 закрыт:
  Track M (ED kernels → затем Serpentine отдельным шагом)
  Track I (per-filter Opacity/Blend)

После A2 закрыт:
  Track H § Angle/Rotation

После C (Bayer/Halftone/CRT стабильны) + A закрыт:
  Track D (GPU)
```

Ничего из добавленного (L, C4.1) не блокирует и не блокируется остальными
треками — оба можно начать в любой момент параллельно с текущей работой
над A/B/C/E/F.
